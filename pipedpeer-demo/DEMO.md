# Pipedpeer live demo — choreography

Goal: prove **zero code changes** and **weak orchestrator** on a 3-node LAN,
with the audience watching the workers burn CPU while the laptop stays flat.

## Layout

```
pipedpeer-demo/
├── 01_sklearn_rf.py      plain sklearn, n_jobs=-1            → joblib backend
├── 02_numpy_heavy.py      np.matmul + np.linalg.svd           → block-slice + offload
├── 03_pandas_ooc.py       read_csv + groupby().mean()         → OOC + hash-shuffle
├── 04_torch_ddp.py        plain torch training loop           → transparent DDP
├── data.csv               generated by setup.sh (~1.7 GB)
├── setup.sh               data + cluster check + rehearsal
└── worker-setup.sh        run once on each worker laptop
```

## Before the audience (15–20 min)

1. On each worker laptop (3 machines): `./worker-setup.sh`
2. On the laptop: `./setup.sh` — generates `data.csv`, prints `pipedpeer nodes`,
   then rehearses all 4 scripts (builds Nix closures, uploads data, materializes
   the store on every worker — this is what makes the live run instant and lets
   pool fan-out reach all 3 workers).
3. Verify: `pipedpeer nodes` shows 4 nodes (self + 3 workers), all `healthy`.
4. Keep rehearsal outputs; they double as "expected values" for the live run.

## Execution commands (live)

| # | Command (run in `pipedpeer-demo/`) |
|---|---|
| 1 | `pipedpeer run 01_sklearn_rf.py --remote --isolate=false` |
| 2 | `pipedpeer run 02_numpy_heavy.py --remote --isolate=false` |
| 3 | `pipedpeer run 03_pandas_ooc.py --remote --isolate=false ` |
| 4 | `pipedpeer run 04_torch_ddp.py --remote --ddp 3 --gpu force --isolate=false` |

Notes:
- `--remote` keeps placement off the laptop (weak orchestrator).
- `--isolate=false` avoids needing crun on worker laptops.
- `` is the pandas interception opt-in (script 3 only).
- `--ddp 3` = 3 transparent gloo ranks; intercept is forced on for DDP.
- First live run per script is instant because setup.sh rehearsed it.
- If a node disappears from `pipedpeer nodes` (no mDNS on some networks):
  `pipedpeer nodes add <worker-ip> 38080`.

## Act 1 — The Code Reveal (2 min)

Open all 4 scripts in the IDE, full-screen. Walk the imports line by line:
`sklearn` / `numpy` / `pandas` / `torch` only. Say the line: *"No SDK, no
pipedpeer import, no Pool wrapper, no rank logic — these run unchanged, and
I'll run them with one command each."* Point at `n_jobs=-1` (01), `np.matmul`
(02), `pd.read_csv` on a 1.7 GB file (03), and the plain training loop (04).

## Act 2 — The Dashboard View (laptop, split terminal)

Split the laptop terminal (tmux/iTerm): left = `pipedpeer dashboard`, right =
the run command. Optionally a third pane: `pipedpeer tasks --watch`.

What to narrate, by metric:

- **Nodes table** — 4 rows (self + 3 workers). Before each run point at
  `MEM AVAIL` (tens of GB on workers).
- **During 01 (joblib/RF)** — `ACTIVE JOBS` on the 3 workers flips to 1 and
  tree-fit batches cycle: worker CPU columns spike, laptop's stays ~0%.
- **During 02 (numpy)** — matmul: watch `MEM AVAIL` drop on all 3 workers as
  the row-block chunks are reserved (≈40 MB per slice), then release as each
  finishes; svd: only ONE worker's `MEM AVAIL` drops (134 MB matrix offload),
  the other two idle — narrate the two distribution models.
- **During 03 (pandas)** — `MEM AVAIL` on workers drops in small waves: the
  CSV is streamed as bounded chunks (0.4x free RAM), and `groupby` buckets are
  hash-shuffled per key so each node reduces its share exactly.
- **During 04 (DDP)** — 3 `ACTIVE JOBS`, one per worker (ranks), for the whole
  training loop.

## Act 3 — The Worker Node View (physical laptops)

On each worker laptop have `htop` full-screen. Key beats:

- **Act 3a (RF):** all 3 workers' cores climb to ~100% in lockstep (tree
  batches land on each). Narrate: *"150 trees, ~50 on each machine, no
  user-side parallelism."*
- **Act 3b (matmul):** the 3 workers alternate in waves — block-sliced rows.
- **Act 3c (svd):** only one worker spikes; its memory climbs to ~700 MB
  (134 MB matrix + LAPACK workspace) then drops. The other two are idle —
  *"single-node heavy offload: some math cannot be split."*
- **Act 3d (pandas):** each worker's CPU spikes in bursts; memory stays
  flat-ish (chunked streaming, worker GC between chunks).
- **Act 3e (DDP):** all 3 spike for the whole run; every ~0.1s they
  synchronize gradients.
- Optional: `tail -f /tmp/pipedpeer/daemon.log` on one worker to show
  `pool/map` requests arriving.

## Act 4 — The Orchestrator Proof (laptop)

After each script, glance at Activity Monitor / Task Manager:

- **CPU:** near 0% during 01, 02, 04 (the CLI streams stdout + results only).
- **RAM:** flat during 03 — the 1.7 GB CSV never touches the laptop (it was
  uploaded once; reads happen on the workers, only the 4-row result comes
  back). Mention `data.csv` next to the script is 1.7 GB and the laptop never
  allocated it.
- **Network:** the only active meter (upload + streaming stdout).
- Closing line: *"the laptop is the orchestrator — it makes decisions and
  streams results, it never does the math."*

## Act 2b — The Traffic Ledger (who sent what to whom)

Every hop now narrates itself:

- **Laptop terminal (the run output):** the shim prints one line per shipped
  operation — `[pipedpeer] matmul: sending N row blocks (134 MB) to cluster`,
  `[pipedpeer] svd: offloading 134 MB matrix to one worker`,
  `[pipedpeer] joblib: dispatching 150 tasks (12 MB) to cluster`,
  `[pipedpeer] read_csv: streaming 1700 MB out-of-core`,
  `[pipedpeer] groupby: hash-shuffling 10,000,000 rows across 4 nodes`.
  These stream live, so the audience reads exactly what the laptop sent.
- **Each worker node:** `tail -f /tmp/pipedpeer/daemon.log` shows its ledger:
  `[pool] received pool/map from 192.168.1.10:...` (who sent it, how many
  items, how much memory reserved) and `[pool] chunk: N items -> M part(s),
  X remote, Y local` when it fans out further.
- **Laptop's own daemon log** (`tail -f /tmp/pipedpeer/daemon.log` on the
  laptop): shows the requests your local daemon received or forwarded.
- **Sent-side history (persisted to disk):** `pipedpeer jobs` then
  `pipedpeer job --id <ID> --output` on the laptop — every submitted job, its
  target node, duration, and exactly which files came back
  (`received_files` / `new_files` / `updated_files`). Stored as JSON under
  `~/.local/share/pipedpeer/jobs/` on the submitting machine.

Choreography beat (1 min, right after Act 4): run 02 again; with the run
terminal + one worker's `tail -f` visible, narrate each hop as it prints —
*"laptop sent the matmul → worker-a received it → split into 8 parts, 7
remote → worker-b/c received the slices → results streamed back."*

Or skip the raw logs entirely — on any node:

```bash
pipedpeer traffic            # last 50 ledger entries of THAT node
pipedpeer traffic -f         # follow live, like tail -f
pipedpeer traffic --limit 200
```

Every node keeps the same ledger in `/tmp/pipedpeer/daemon.log` (or
`$PIPEDPEER_DAEMON_STATE_DIR`). Retention: completed jobs are pruned
automatically — the daemon sweeps its finished job dirs hourly (7-day
retention) and the laptop's history too:

```bash
pipedpeer jobs prune                       # delete history older than 7 days
pipedpeer jobs prune --older-than 24h      # ...or whatever you prefer
```

## Act 5 — Fault tolerance (optional, 1 min)

Run 02 again, and 10 s in, `pipedpeer stop` on ONE worker laptop. Point at the
dashboard: the node flips unhealthy, its chunk is rescheduled (lease expiry +
retry), the run still completes. `pipedpeer start` on that worker afterwards.

## Troubleshooting

- **Run hangs at upload** → the 2 GB workspace (data.csv) is shipping; it is
  normal on the first 03 run, ~20–30 s on gigabit LAN.
- **`pipedpeer nodes` empty on workers** → mDNS blocked; add manually with
  `pipedpeer nodes add <host> 38080` on the orchestrator.
- **Pool fan-out silent / local-only** → peers must already have the closure;
  re-run `setup.sh` rehearsal. (Spill only targets nodes whose store is
  materialized — by design.)
- **DDP ranks fail to rendezvous** → the leader (rank 0) hosts the meet-up on
  port 29500 (next free up to 29510 if busy). Open the range once on each
  worker: `sudo ufw allow 29500:29510/tcp`. Ranks fail within ~2 min with a
  clear timeout instead of hanging; `--ddp-port` pins an exact port.
- **Isolation errors (crun missing)** → you forgot `--isolate=false`.
- **First run still slow** → closures build in the rehearsal; if you skipped
  it, expect minutes of `[1/7]`/`[2/7]` Nix work on the first live run.
