# Pipedpeer live demo — choreography

Goal: prove **zero code changes** on a 2-node LAN — the orchestrator machine
plus one worker, both with an NVIDIA dGPU — with the audience watching plain
Python scripts spread across both machines and light up both GPUs.

## Layout

```
pipedpeer-demo/
├── 01_sklearn_rf.py      plain sklearn, n_jobs=-1            → joblib backend
├── 02_numpy_heavy.py      np.matmul + np.linalg.svd           → block-slice + offload
├── 03_pandas_ooc/         read_csv + groupby().mean()         → OOC + hash-shuffle
│   └── data.csv           generated by setup.sh (~1.7 GB); own workspace so
│                          only 03 ships it
├── 04_torch_ddp.py        plain torch training loop           → transparent DDP
├── 05_file_sync.py        create/modify/delete on the worker  → workspace sync-back
├── setup.sh               data + cluster check + rehearsal
└── worker-setup.sh        run once on the worker machine
```

## Before the audience (15–20 min)

1. On the worker machine: `./worker-setup.sh`
2. On the orchestrator: `./setup.sh` — generates `data.csv`, prints
   `pipedpeer nodes`, then rehearses all 4 scripts (builds Nix closures,
   uploads data, materializes the store on the worker — this is what makes the
   live run instant and lets pool fan-out reach it).
3. Verify: `pipedpeer nodes` shows 2 nodes (self + worker), both `healthy`,
   and the GPU column lists the NVIDIA card on BOTH rows.
4. Keep rehearsal outputs; they double as "expected values" for the live run.

## Execution commands (live)

| # | Command (run in `pipedpeer-demo/`) |
|---|---|
| 1 | `pipedpeer run 01_sklearn_rf.py --remote` |
| 2 | `pipedpeer run 02_numpy_heavy.py --remote` |
| 3 | `pipedpeer run 03_pandas_ooc/03_pandas_ooc.py --remote` |
| 4a | `pipedpeer run 04_torch_ddp.py --remote --ddp 2 --gpu off` — BOTH machines train as CPU ranks |
| 4b | `pipedpeer run 04_torch_ddp.py --remote --ddp 2` — same script again, now one rank per dGPU |
| 5 | `pipedpeer run 05_file_sync.py --remote` — runs on the worker; the file changes it makes there sync back to the orchestrator |

Notes:
- That's the whole workflow: the exact script you'd run locally, plus
  `--remote`. No SDK, no imports, no rewrites.
- Interception is always on — numpy/pandas/sklearn/torch calls route to the
  cluster when the cost model says the cluster wins. GPU use is inferred from
  the script's imports, so 04 lands on GPUs without any flag.
- Torch runs twice on purpose: 4a (`--gpu off`) trains one CPU rank per
  machine — proof the ring works on any hardware; 4b is the identical script
  with GPUs inferred from the torch import — one rank per dGPU, same loss,
  much faster epochs.
- Rank sync travels over the daemons' normal port (`/v1/ddp/sync`) — no
  extra ports, no firewall prep. Narrate that: *"the gradient sync uses the
  same single channel every other byte uses."*
- Isolation is automatic too: nodes with crun sandbox jobs, nodes without it
  run unisolated with a one-line warning.
- First live run per script is instant because setup.sh rehearsed it.
- If a node disappears from `pipedpeer nodes` (no mDNS on some networks):
  `pipedpeer nodes add <worker-ip> 38080`. Discovery now also sweeps the
  subnet over HTTP, so this should rarely be needed.
- Dead or leftover entries in `pipedpeer nodes`? Remove one with
  `pipedpeer nodes remove <host-or-node-id>` (the 8-char short ID from the
  list works) — run it on every machine that shows the ghost.

## Act 1 — The Code Reveal (2 min)

Open all 4 scripts in the IDE, full-screen. Walk the imports line by line:
`sklearn` / `numpy` / `pandas` / `torch` only. Say the line: *"No SDK, no
pipedpeer import, no Pool wrapper, no rank logic — these run unchanged, and
I'll run them with one command each."* Point at `n_jobs=-1` (01), `np.matmul`
(02), `pd.read_csv` on a 1.7 GB file (03), and the plain training loop (04).

## Act 2 — The Dashboard View (orchestrator, split terminal)

Split the orchestrator terminal (tmux/iTerm): left = `pipedpeer dashboard`,
right = the run command. Optionally a third pane: `pipedpeer tasks --watch`.

What to narrate, by metric:

- **Nodes table** — 2 rows (self + worker). Before each run point at
  `MEM AVAIL` and the GPU column on both rows.
- **During 01 (joblib/RF)** — `ACTIVE JOBS` on the worker flips to 1 and
  tree-fit batches cycle between the two machines: both CPU columns spike as
  the batches split local/remote.
- **During 02 (numpy)** — matmul: watch `MEM AVAIL` drop on the worker as
  row-block chunks are reserved (≈40 MB per slice), then release as each
  finishes; svd: the whole 134 MB matrix offloads to one node — narrate the
  two distribution models (splittable vs. ship-it-whole).
- **During 03 (pandas)** — worker `MEM AVAIL` drops in small waves: the CSV
  is streamed as bounded chunks (0.4x free RAM), and `groupby` buckets are
  hash-shuffled per key so each node reduces its share exactly.
- **During 4a (CPU DDP)** — 2 `ACTIVE JOBS`, one rank per machine; both CPU
  columns climb together for the whole run.
- **During 4b (GPU DDP)** — 2 `ACTIVE JOBS` again, but now `nvidia-smi` on
  each machine shows the python process and the CPU columns stay low — same
  script, the ranks just landed on CUDA.

## Act 3 — The Worker Node View (physical machines)

On the worker have `htop` full-screen (and `nvidia-smi -l 1` for 4b). Key
beats:

- **Act 3a (RF):** both machines' cores climb in lockstep (tree batches land
  on each). Narrate: *"150 trees split across the machines, no user-side
  parallelism."*
- **Act 3b (matmul):** the worker spikes in waves — block-sliced rows
  arriving as chunks.
- **Act 3c (svd):** one machine spikes alone; its memory climbs to ~700 MB
  (134 MB matrix + LAPACK workspace) then drops —
  *"single-node heavy offload: some math cannot be split."*
- **Act 3d (pandas):** the worker's CPU spikes in bursts; memory stays
  flat-ish (chunked streaming, worker GC between chunks).
- **Act 3e (4a CPU DDP):** both machines spike together for the whole run.
- **Act 3f (4b GPU DDP):** both GPUs light up (`nvidia-smi` shows the python
  process on each), CPUs go quiet; same script, ~20x faster epochs.
- Optional: `tail -f /tmp/pipedpeer/daemon.log` on the worker to show
  `pool/map` requests arriving.

## Act 4 — The Orchestrator Proof

After 03, glance at the orchestrator's Task Manager / Activity Monitor:

- **RAM:** flat during 03 — the 1.7 GB CSV never touches the orchestrator's
  Python (it was uploaded once; reads happen out-of-core, only the 4-row
  result comes back).
- **Network:** the active meter during uploads and streaming stdout.
- Closing line: *"the submitting machine makes decisions and streams
  results — the heavy math went wherever the scheduler put it."*

## Act 2b — The Traffic Ledger (who sent what to whom)

Every hop narrates itself:

- **Orchestrator terminal (the run output):** the shim prints one line per
  shipped operation — `[pipedpeer] matmul: sending N row blocks (134 MB) to
  cluster`, `[pipedpeer] svd: offloading 134 MB matrix to one worker`,
  `[pipedpeer] joblib: dispatching 150 tasks (12 MB) to cluster`,
  `[pipedpeer] read_csv: streaming 1700 MB out-of-core`,
  `[pipedpeer] groupby: hash-shuffling 10,000,000 rows across 2 nodes`.
  These stream live, so the audience reads exactly what was sent.
- **Worker:** `tail -f /tmp/pipedpeer/daemon.log` shows its ledger:
  `[pool] received pool/map from 192.168.x.x:...` (who sent it, how many
  items, how much memory reserved) and `[pool] chunk: N items -> M part(s),
  X remote, Y local` when it fans out further.
- **Orchestrator's own daemon log** (`tail -f /tmp/pipedpeer/daemon.log`):
  the requests the local daemon received or forwarded.
- **Sent-side history (persisted to disk):** `pipedpeer jobs` then
  `pipedpeer job --id <ID> --output` on the orchestrator — every submitted
  job, its target node, duration, and exactly which files came back
  (`received_files` / `new_files` / `updated_files`). Stored as JSON under
  `~/.local/share/pipedpeer/jobs/` on the submitting machine.

Choreography beat (1 min, right after Act 4): run 02 again; with the run
terminal + the worker's `tail -f` visible, narrate each hop as it prints —
*"orchestrator sent the matmul → worker received it → split into parts, half
remote, half local → results streamed back."*

Or skip the raw logs entirely — on any node:

```bash
pipedpeer traffic            # last 50 ledger entries of THAT node
pipedpeer traffic -f         # follow live, like tail -f
pipedpeer traffic --limit 200
```

Every node keeps the same ledger in `/tmp/pipedpeer/daemon.log` (or
`$PIPEDPEER_DAEMON_STATE_DIR`). Retention: completed jobs are pruned
automatically — the daemon sweeps its finished job dirs hourly (7-day
retention) and the orchestrator's history too:

```bash
pipedpeer jobs prune                       # delete history older than 7 days
pipedpeer jobs prune --older-than 24h      # ...or whatever you prefer
```

## Distribution levers (rehearsal insurance)

`auto` (the default) is the honest mode: the cost model ships work only when
the cluster wins, so on a fast LAN the demos distribute on their own. If a
gate declines something you want shown, force it:

```bash
pipedpeer run 01_sklearn_rf.py --distribute force     # every gate says yes
pipedpeer run ... -e PIPEDPEER_SPILL_MIN=1000000      # explicit size floor (bytes)
```

Force skips the cost models and zeroes the 32 MB size floors — it can be
slower than local (that is the point of the default), so on stage prefer
`auto` first and keep `force` as the guarantee that the dashboards light up.

## Act 5 — Fault tolerance (optional, 1 min)

Run 02 again, and 10 s in, `pipedpeer stop` on the worker. Point at the
dashboard: the node flips unhealthy, its chunk is rescheduled (lease expiry +
retry), the run still completes locally. `pipedpeer start` on the worker
afterwards.

## Troubleshooting

- **Run hangs at upload** → the 2 GB workspace (data.csv) is shipping; it is
  normal on the first 03 run, ~20–30 s on gigabit LAN.
- **`pipedpeer nodes` empty** → mDNS blocked; add manually with
  `pipedpeer nodes add <worker-ip> 38080` on the orchestrator.
- **Pool fan-out silent / local-only** → the peer must already have the
  closure; re-run `setup.sh` rehearsal. (Spill only targets nodes whose store
  is materialized — by design.)
- **DDP ranks fail to sync** → sync rides the lead rank's daemon
  (`/v1/ddp/sync` on port 38080), so if `pipedpeer nodes` is healthy DDP has
  everything it needs — check `pipedpeer traffic` on the lead node for the
  arriving sync posts. Port 29500 only matters if you force the old
  transport with `PIPEDPEER_DDP_BACKEND=gloo`.
- **4b trains on CPU despite the GPU** → check `nvidia-smi` works outside
  pipedpeer first (driver up?); the sandbox injects `/dev/nvidia*` and the
  driver libraries automatically, so a working host driver is all it needs.
- **Worker rejects uploaded closures** (`lacks a signature by a trusted key`)
  → that worker runs multi-user nix and was set up with an old build. Re-run
  `pipedpeer setup -y` there: the nix-imports prerequisite now repairs the
  config itself (require-sigs = false + nix-daemon restart, one sudo prompt).
- **Isolation errors (crun missing)** → none possible: the node warns and
  runs unisolated. Install crun (`pipedpeer setup`) to get sandboxing back.
- **First run still slow** → closures build in the rehearsal; if you skipped
  it, expect minutes of `[1/7]`/`[2/7]` Nix work on the first live run.
