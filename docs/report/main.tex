\begin{center}
  {\Large\bfseries Abstract}
\end{center}
\vspace{1cm}

\noindent This project presents \textbf{PipedPeer}, a system that runs an unmodified Python script on other machines, with no cluster to configure and no manual installation: one binary, whose set-up command installs the rest (Nix and an OCI runtime) if absent, without root if need be. Three problems normally stand between a developer and the idle machines around them: reproducing the script's environment elsewhere, rewriting the program against a cluster API, and reaching machines that sit behind different routers. PipedPeer removes all three.

\noindent The environment is reproduced by building a \textbf{Nix closure} against a pinned package set, so the same script yields the same content-addressed store path on every machine and on any day. A worker that already holds an environment pays nothing to set it up again, and one that holds part of it receives only the store paths it lacks. Measured on a three-worker container lab, the first submission of a job took 23.4 seconds, and later submissions that found the environment already in place took a median of 0.83 seconds.

\noindent The program is distributed by \textbf{intercepting the parallel primitives it already uses}. A shim injected into the job's interpreter replaces \texttt{multiprocessing.Pool}, pandas \texttt{groupby} and \texttt{merge}, chunked file readers, NumPy linear algebra, \texttt{joblib} and torch data-parallel training. Pool kernels travel as source or, for lambdas and closures, by value through cloudpickle. Work is shared between machines in proportion to their measured throughput, and a cost model ships numerical work only when computing locally would cost more than moving it. Every remote path degrades to the local one, with one deliberate exception: a matrix product that fits neither locally nor on the cluster raises an error rather than exhausting the machine.

\noindent Machines on different networks are joined with one command. A small introducer exchanges candidate addresses; the machines then ask their routers for a port mapping or punch through them, falling back to a birthday-collision search for the hardest pair of NATs, and carry all traffic over a direct, mutually authenticated QUIC link. No relay carries job data. Each daemon's API is protected by an optional shared secret and pinned TLS, closures are signed with each node's ed25519 key, and jobs run by default in a \texttt{crun} sandbox under their own memory ceiling where the node supports it. A run can be watched (a plain-language events feed, CPU and GPU load per node, a closing summary of where its work ran), checked beforehand by a dry run, stopped everywhere with one interrupt, or detached and reattached later; a training ring continues when a rank dies and takes back a machine that returns. Of \textbf{829} tests, \textbf{822} pass, \textbf{0} fail and \textbf{7} are skipped; % evidence fix5/go-test-json.jsonl (cc56753, go test -count=1 -p 1 -json ./..., top-level tests)
a mutation audit that breaks 95 features one at a time is caught by the tests in every case. A fault-injection run on the container lab did not distribute work and so did not test recovery, and is reported as such. Speedups between real machines are reported only as recorded during development, with their provenance, and are not claimed beyond them.

\vspace{1cm}
\noindent\textbf{Keywords:} Distributed Computing, Peer-to-Peer, NAT Traversal, Transparent Interception, Nix, Content-Addressed Caching, OCI Sandboxing, Cost-Based Scheduling, Fault Tolerance.

\chapter{Introduction}

\section{Problem Statement}

A developer with a laptop, a lab workstation and a spare desktop has a
considerable amount of idle computing capacity and no practical way to use it.
The frameworks that exist for distributed computation --- Apache Spark
\cite{zaharia2010spark}, Ray \cite{moritz2018ray}, Dask \cite{rocklin2015dask}
--- all presuppose a cluster that somebody has already configured: a head node,
matching software on every worker, a scheduler process, and a network on which
every machine can reach every other. Ordinary machines fail the last of these:
each sits behind its own home or campus router and accepts no inbound
connection.
For a team that simply wants a script to finish sooner, that setup costs more
than the job is worth. The alternative, \texttt{ssh} together with
\texttt{rsync}, means reproducing the environment by hand on every machine and
receiving no scheduling, no isolation and no fault tolerance in return.

Three distinct problems sit underneath this, and they are usually attacked
separately:

\begin{enumerate}[leftmargin=*, label=\arabic*.]
  \item \textbf{The environment problem.} A script needs a particular
  interpreter and a particular set of libraries. Making a remote machine match
  the local one is the bulk of the work, and it is the reason ``just \texttt{ssh}
  into it'' does not scale past a single machine.
  \item \textbf{The code problem.} Even with a matching environment, using more
  than one machine normally means rewriting the program against a cluster API.
  A script that took an afternoon to write becomes a project.
  \item \textbf{The reachability problem.} Machines on different networks cannot
  open a connection to one another without a VPN, port forwarding, or a relay
  that carries every byte between them.
\end{enumerate}

\textbf{\projecttitle} addresses all three without asking the user to change
the program. The environment is reproduced exactly by shipping a Nix closure; the
program is distributed without modification by intercepting the parallel
primitives it already uses; and machines on different networks are joined by
punching a direct path through their routers, with a small introducer that only
tells each machine where the others are.

\section{Objectives}

\begin{enumerate}[leftmargin=*, label=\arabic*.]
  \item To run an unmodified Python script on the best available machine on the
  network, with results appearing in the user's working directory as though the
  script had run locally.
  \item To reproduce the script's environment exactly on that machine, sending
  only the store paths that machine does not already hold.
  \item To choose the machine from live capacity, treating architecture and GPU
  availability as hard requirements and load, memory and hardware as a ranking.
  \item To distribute the parallel work inside the script across the cluster
  with no code changes, only when doing so is expected to be faster than running
  it locally, and in proportion to each machine's measured throughput.
  \item To join machines on different networks into one cluster with a single
  command, with no VPN, no port forwarding and no relay in the data path.
  \item To protect each node's API with a shared secret and its traffic with
  encryption, to isolate each job, and to survive the loss of any worker without
  losing the run.
  \item To require no manual installation on a new machine: one binary, whose
  set-up command installs what else is needed, without root if necessary.
\end{enumerate}

\section{Scope}

The following are within scope and implemented:

\begin{itemize}[leftmargin=*]
  \item A Go daemon that performs peer discovery, placement, leasing, sandboxed
  execution and result delivery, and a thin CLI client.
  \item Peer discovery by UDP multicast and broadcast on the local subnet, with
  a TCP health-probe sweep as a fallback and an optional standalone registry.
  \item Joining across networks: an introducer, router port mapping (PCP,
  NAT-PMP, UPnP-IGD), UDP hole punching with a birthday-collision fallback, and
  direct QUIC links authenticated by each node's ed25519 key.
  \item An optional cluster-wide shared secret on every API route, pinned TLS on
  the daemon port, and closures signed with each node's key.
  \item Reproducible environments built as Nix closures against a pinned package
  set, cached by store path, and transferred as a path-level difference against
  what the receiving node already holds.
  \item Placement by hard filters on architecture, GPU, memory, cores and VRAM,
  followed by a score over live load and hardware, with a three-phase lease.
  \item Per-job isolation in a \texttt{crun} OCI sandbox under a per-job memory
  ceiling, including GPU device and driver passthrough, runnable without root.
  \item Transparent interception of \texttt{multiprocessing.Pool}, pandas
  \texttt{groupby}, \texttt{merge} and chunked readers, NumPy linear algebra,
  \texttt{joblib} and scikit-learn, and torch data-parallel training, with work
  shared by measured throughput and numerical work governed by a cost model.
  \item Result synchronisation of changed files only, with deletions carried in
  a manifest, and a live terminal dashboard.
\end{itemize}

The following are explicitly out of scope in the current implementation:
per-user authorisation (a cluster shares one secret; Section~\ref{sec:security}),
runtimes other than Python, relaying traffic for a peer that no direct path can
reach (such a peer is reported and routed around), and any economic incentive
mechanism.

\section{Assumptions and Constraints}

\begin{itemize}[leftmargin=*]
  \item Every participating machine runs the same binary.
  \texttt{pipedpeer setup} installs Nix and \texttt{crun} when they are missing,
  and can do so without root by using a private Nix store.
  \item Workers run Linux, since \texttt{crun}, cgroups and the Nix store are
  Linux-specific. The submitting side also builds for macOS as a client.
  \item Machines in a cluster share one secret, created by the first machine's
  set-up before its daemon first starts and carried to the others by an invite
  code (Section~\ref{sec:security}).
  \item Joining across networks needs one reachable introducer. Every daemon is
  one for its own cluster, and a public server can serve as one that takes no
  jobs. Introducers carry no job data.
  \item Two machines between which no direct path exists cannot work together;
  the peer is reported and routed around rather than relayed.
  \item The submitting process must remain alive for the duration of a job: it
  holds the lease and receives the output stream.
\end{itemize}

% ============================================================
\chapter{Literature Survey}
\label{chap:lit}
% ============================================================

This chapter surveys work across the areas PipedPeer draws on: lightweight
sandboxing and environment portability at the edge, messaging and actor-style
fault tolerance, failure-transparent programming models, portability in the
Python ecosystem, scheduling, and collaborative task offloading. Each entry
closes with the bearing it has on the design decisions taken in
Chapters~\ref{chap:arch} and~\ref{chap:design}.

\subsection*{Paper 1: Web Application-Based WebAssembly Container Platform for Extreme Edge Computing}
\addcontentsline{toc}{subsection}{Paper 1}
\textbf{Authors:} S.~Sekigawa, C.~Sasaki, A.~Tagami \quad
\textbf{In:} Proc.\ IEEE GLOBECOM, 2023~\cite{sekigawa2023}

\noindent\textbf{Summary:} A platform that deploys WebAssembly modules as
isolated compute units on edge nodes, sandboxing and executing user-submitted
binaries without a container daemon such as Docker. Evaluation on constrained
hardware shows acceptable latency with strong isolation.

\noindent\textbf{Bearing on this work:} The paper's argument that a lightweight
sandbox can replace a full container runtime is the one PipedPeer follows, but
the conclusion differs. PipedPeer must run arbitrary CPython with native
extensions, which Wasm cannot host, so it takes an OCI runtime (\texttt{crun})
directly rather than a bytecode sandbox. Section~\ref{sec:sandbox} measures what
that choice costs: roughly 20\,ms per job.

\subsection*{Paper 2: WebAssembly for Edge Computing: Potential and Challenges}
\addcontentsline{toc}{subsection}{Paper 2}
\textbf{Authors:} M.~N.~Hoque, K.~A.~Harras \quad
\textbf{In:} IEEE Commun.\ Standards Mag., vol.~6, no.~4, 2022~\cite{hoque2022}

\noindent\textbf{Summary:} A survey weighing Wasm's near-native speed and memory
sandboxing against containers and VMs, identifying WASI immaturity, limited
file-system and networking APIs, and absent GPU support as the blocking gaps.

\noindent\textbf{Bearing on this work:} These gaps are precisely why PipedPeer
ships a complete native environment as a Nix closure rather than compiling user
code to a portable bytecode. A Nix closure carries native dependencies and GPU
libraries intact, which is a hard requirement for the machine-learning workloads
in Section~\ref{sec:workloads}.

\subsection*{Paper 3: A Cross-Architecture Evaluation of WebAssembly in the Cloud-Edge Continuum}
\addcontentsline{toc}{subsection}{Paper 3}
\textbf{Authors:} S.~Kakati, M.~Brorsson \quad
\textbf{In:} Proc.\ IEEE/ACM CCGrid, 2024~\cite{kakati2024}

\noindent\textbf{Summary:} Benchmarks Wasm runtimes across x86\_64, ARM64 and
RISC-V, reporting 70--90\% of native performance and sub-10\,ms startup, with
I/O-bound workloads suffering disproportionately from WASI syscall translation.

\noindent\textbf{Bearing on this work:} PipedPeer targets heterogeneous
architectures too, but resolves them at build time rather than at run time: the
flake generator emits an architecture-specific closure, and architecture is a
\emph{hard filter} during placement (Section~\ref{sec:placement}) rather than
something the runtime papers over. Full native performance is retained.

\subsection*{Paper 4: Design of Elixir-Based Edge Server for Responsive IoT Applications}
\addcontentsline{toc}{subsection}{Paper 4}
\textbf{Authors:} Y.~Li, S.~Fujita \quad
\textbf{In:} Proc.\ IEEE CANDARW, 2022~\cite{li2023elixir}

\noindent\textbf{Summary:} An IoT edge server built on Elixir and OTP, where
supervisor trees restart failed processes automatically and the system stays
available through individual crashes.

\noindent\textbf{Bearing on this work:} Supervision is the model PipedPeer's
retry loop follows: a failed placement is retried on the next-best node with
exponential backoff, and the work is never dropped. The difference is where
recovery state lives. PipedPeer has no supervisor process; recovery falls out of
lease expiry (Section~\ref{sec:lease}), so there is nothing whose own failure
needs supervising.

\subsection*{Paper 5: A Synergistic Elixir-EDA-MQTT Framework for Smart Transportation}
\addcontentsline{toc}{subsection}{Paper 5}
\textbf{Authors:} Y.~Li, S.~Fujita \quad
\textbf{In:} Future Internet, vol.~16, no.~3, 2024~\cite{zhou2024}

\noindent\textbf{Summary:} Combines Elixir concurrency, event-driven
architecture and MQTT publish-subscribe, showing lower overhead than REST for
high-frequency telemetry.

\noindent\textbf{Bearing on this work:} An earlier iteration of PipedPeer used
publish-subscribe messaging (NATS) as its dispatch transport for exactly the
reasons this paper gives. Experience moved the system the other way: bulk
transfer of closures, workspaces and results needs streaming and backpressure,
so dispatch is now plain HTTP with a WebSocket for output, and messaging is
retained only as an optional transport for small lease messages. The paper
documents the case for the road not taken.

\subsection*{Paper 6: WebAssembly with wasi-nn for Edge Machine Learning Inference}
\addcontentsline{toc}{subsection}{Paper 6}
\textbf{Authors:} J.~Bachmeier, V.~Yussupov, J.~Hen\ss, H.~Koziolek \quad
\textbf{In:} Proc.\ ECSA, 2025~\cite{bachmeier2025}

\noindent\textbf{Summary:} Evaluates Wasm with wasi-nn for edge inference,
finding good portability for CPU inference and immaturity for GPU acceleration.

\noindent\textbf{Bearing on this work:} Machine-learning jobs are a primary use
case, which is why \texttt{torch} and \texttt{tensorflow} carry the largest
entries in PipedPeer's memory-estimation table and why GPU passthrough is
implemented at the OCI level. This paper's negative result on GPU support under
Wasm supports the decision to ship a native CUDA-capable environment instead.

\subsection*{Paper 7: Case Study of WebAssembly Runtimes for AI Applications on the Edge}
\addcontentsline{toc}{subsection}{Paper 7}
\textbf{Authors:} S.~E.~Khelifa, M.~Bagaa, A.~O.~Messaoud, A.~Ksentini \quad
\textbf{In:} Proc.\ GIIS, 2024~\cite{khelifa2024}

\noindent\textbf{Summary:} Compares four Wasm runtimes for AI inference on edge
devices, finding memory consumption to be the dominant constraint.

\noindent\textbf{Bearing on this work:} Memory as the binding constraint is the
assumption behind PipedPeer's tiered memory estimator and behind admission
control: a node refuses a job it cannot hold, the pool executor splits a
request that would exceed 40\% of available memory into sequential chunks
instead of failing, and on a node with a usable cgroup hierarchy every job runs
under its own memory ceiling inside a daemon that is itself capped
(Section~\ref{sec:sandbox}).

\subsection*{Paper 8: Programming Models for Failure-Transparent Distributed Systems}
\addcontentsline{toc}{subsection}{Paper 8}
\textbf{Authors:} J.~Spenger \quad
\textbf{In:} Ph.D.\ dissertation, KTH Royal Institute of Technology, 2025~\cite{kth2025thesis}

\noindent\textbf{Summary:} Gives a definition of failure transparency, masking
failures fully from the programmer, that does not depend on a particular
semantics; proves it for a model of stateful dataflow streaming; and builds two
programming models on that base, one for compositional patterns and one with
windowed conflict-free replicated data types for global aggregations.

\noindent\textbf{Bearing on this work:} Failure transparency is PipedPeer's
central invariant. The user's script contains no failure handling at all, so
every remote path must degrade to a working local one. PipedPeer enforces this by
fallback and tests rather than proof: Section~\ref{sec:ft} sets out the five
layers, and Section~\ref{sec:res-ft} shows a worker being killed mid-computation
without affecting the result.

\subsection*{Paper 9: Python Array API Standard}
\addcontentsline{toc}{subsection}{Paper 9}
\textbf{Authors:} A.~Meurer et al. \quad
\textbf{In:} Proc.\ SciPy, 2023~\cite{arrayapi2023}

\noindent\textbf{Summary:} A standardised array API letting the same code run on
NumPy, CuPy or JAX without modification, so scripts become portable across
computational backends.

\noindent\textbf{Bearing on this work:} The goal is the same as PipedPeer's ---
portability without code change --- but the mechanism is the mirror image. The
Array API asks libraries to converge on one interface that users then adopt.
PipedPeer changes nothing the user writes and instead substitutes the
implementations behind the interfaces they already use. The comparison is drawn
out in Section~\ref{sec:comparison}.

\subsection*{Paper 10: iDDS: Intelligent Distributed Dispatch and Scheduling}
\addcontentsline{toc}{subsection}{Paper 10}
\textbf{Authors:} W.~Guan et al. \quad
\textbf{In:} arXiv:2510.02930, 2025~\cite{idds2025}

\noindent\textbf{Summary:} Workflow orchestration that assigns tasks to
heterogeneous resources from real-time CPU, memory, data-locality and dependency
constraints, driven by a task DAG.

\noindent\textbf{Bearing on this work:} The scoring-based assignment is directly
comparable to the placement function in Section~\ref{sec:placement}. Two
differences are worth stating: PipedPeer has no DAG, because it schedules whole
scripts rather than task graphs, and it has no scheduler process at all, the
scoring being performed in the submitting client. Data locality, which iDDS
treats as first-class, is absent from PipedPeer's placement and is noted as
future work.

\subsection*{Paper 11: Task Offloading in Multi-Hop Relay-Aided Multi-Access Edge Computing}
\addcontentsline{toc}{subsection}{Paper 11}
\textbf{Authors:} Y.~Deng, Z.~Chen, X.~Chen, Y.~Fang \quad
\textbf{In:} IEEE Trans.\ Veh.\ Technol., vol.~72, no.~1, 2023~\cite{deng2023}

\noindent\textbf{Summary:} Formulates joint task assignment and relay selection
to minimise completion time under transmission and energy constraints.

\noindent\textbf{Bearing on this work:} The offload-or-compute-locally trade-off
is exactly what PipedPeer's cost model decides, and this paper's formulation of
it as a comparison between transmission time and local computation time is the
same shape as the inequality in Section~\ref{sec:cost}. PipedPeer measures link
bandwidth at run time rather than assuming a channel model, and for parallel
maps it goes further, fitting each peer's set-up time and throughput from the
work it has actually returned.

\subsection*{Paper 12: Multi-Agent Deep Reinforcement Learning Based Dynamic Task Offloading}
\addcontentsline{toc}{subsection}{Paper 12}
\textbf{Authors:} H.~He, X.~Yang, X.~Mi, H.~Shen, X.~Liao \quad
\textbf{In:} Sensors, vol.~24, no.~16, 2024~\cite{he2024}

\noindent\textbf{Summary:} Each device learns an offloading policy from local
observations without a central coordinator, beating centralised heuristics on
the energy-delay trade-off.

\noindent\textbf{Bearing on this work:} This establishes the ceiling PipedPeer's
deterministic rule-based model gives up. The trade is deliberate: a learned
policy needs training data and a training phase, which is incompatible with a
tool whose value proposition is that a new machine joins by running one binary.
It is a natural direction once a deployment produces enough history.

\subsection*{Paper 13: Joint Optimization of Multi-User Partial Offloading and Resource Allocation}
\addcontentsline{toc}{subsection}{Paper 13}
\textbf{Authors:} D.~Yong, R.~Liu, X.~Jia, Y.~Gu \quad
\textbf{In:} Sensors, vol.~23, no.~5, 2023~\cite{yong2023}

\noindent\textbf{Summary:} Optimises the split between locally executed and
offloaded portions of a task, finding partial offloading consistently better
than all-or-nothing.

\noindent\textbf{Bearing on this work:} This paper describes what PipedPeer now
does. Interception splits a single script's work across nodes at the granularity
of \texttt{Pool} chunks, hash-shuffle buckets and matrix row blocks, while the
remainder runs locally --- partial offloading in the sense used here. The split
is chosen as this paper recommends, by minimising completion time: each peer's
share comes from a makespan solver over measured rates
(Section~\ref{sec:intercept}). The racing
scheme in Section~\ref{sec:ft} goes further by keeping the local share
speculative, so an unresponsive remote share costs nothing.

\subsection*{Paper 14: Energy-Efficient Collaborative Task Offloading in MEC}
\addcontentsline{toc}{subsection}{Paper 14}
\textbf{Authors:} S.~Wang et al. \quad
\textbf{In:} Ad Hoc Networks, vol.~169, 2025~\cite{adhoc2025}

\noindent\textbf{Summary:} Devices cooperate by relaying tasks toward edge
servers, with a learned policy cutting total energy against non-cooperative
baselines.

\noindent\textbf{Bearing on this work:} The symmetric model, where every device
is both client and server, is PipedPeer's model too: one binary, and any node
may submit or accept. PipedPeer also forwards a parallel-map request that a node
cannot hold to a healthier peer rather than refusing it.

\subsection*{Paper 15: Blockchain Enabled Task Offloading in Digital Twin Vehicular Edge Networks}
\addcontentsline{toc}{subsection}{Paper 15}
\textbf{Authors:} C.~Li, Q.~Chen, M.~Chen, Z.~Su, Y.~Ding, D.~Lan, A.~Taherkordi \quad
\textbf{In:} J.\ Cloud Comput., vol.~12, Art.~no.~120, 2023~\cite{li2023blockchain}

\noindent\textbf{Summary:} Smart contracts enforce service agreements between
task submitters and edge workers, preventing free-riding in an untrusted
network.

\noindent\textbf{Bearing on this work:} PipedPeer now authenticates who may use a
node, with a cluster-wide shared secret, encrypted links and signed closures
(Section~\ref{sec:trust}). It does not address what this paper addresses, which
is whether a participant that \emph{is} admitted behaves well: every holder of
the secret can run arbitrary code on every node, and nothing accounts for or
rewards contribution. The paper describes the class of mechanism that would be
needed for a cluster of mutually untrusting owners, and its commit-and-verify
structure resembles the existing three-phase lease.

\subsection*{Paper 16: Congestion-Aware Distributed Task Offloading Using Graph Neural Networks}
\addcontentsline{toc}{subsection}{Paper 16}
\textbf{Authors:} Z.~Zhao, J.~Perazzone, G.~Verma, S.~Segarra \quad
\textbf{In:} Proc.\ IEEE ICASSP, 2024~\cite{zhao2023}

\noindent\textbf{Summary:} Trains a graph neural network to produce distributed
offloading policies from local neighbourhood observations, outperforming greedy
baselines under congestion.

\noindent\textbf{Bearing on this work:} PipedPeer scores each node independently
on scalar metrics and is therefore blind to topology: two nodes with identical
load score identically even if one is a slow hop away. Link cost is measured,
but only where work is divided --- in the cost model's bandwidth probe and in the
per-peer set-up time fitted for parallel maps --- and not when a whole job is
placed. Feeding a graph-structured view into placement is the most concrete
extension this survey suggests.

\section*{Standards Underlying Cross-Network Operation}
\addcontentsline{toc}{section}{Standards Underlying Cross-Network Operation}

Joining machines on different networks (Section~\ref{sec:nat}) rests on
established standards rather than on new mechanisms, and the design follows
them closely. Address discovery uses the reflexive-address idea of STUN
\cite{rfc8489}, and the \texttt{nattype} package classifies a
router's mapping and filtering behaviour in the terms of RFC~5780
\cite{rfc5780}. Port mapping requests follow NAT-PMP \cite{rfc6886}, its
successor PCP \cite{rfc6887}, and UPnP Internet Gateway Device \cite{upnpigd}.
Simultaneous UDP probing from the socket that will carry the connection is the
hole-punching technique analysed by Ford, Srisuresh and Kegel \cite{ford2005p2p},
whose central observation --- that a router's mapping belongs to a socket, so the
probe and the connection must share one --- shapes PipedPeer's shared-socket
design. Links are QUIC \cite{rfc9000} secured by TLS~1.3 \cite{rfc8446}, node
identities are Ed25519 keys \cite{bernstein2012ed25519}, and archives are
compressed with Zstandard \cite{rfc8878}.

\section{System Architecture}

PipedPeer follows a \textbf{daemon, not CLI} architecture. Every machine runs
one long-lived daemon that handles discovery, admission, execution and result
delivery. The \texttt{pipedpeer} command is a short-lived client.

One consequence is worth stating early because it distinguishes the system from
every framework in Chapter~2: \textbf{the coordinator is a library linked into
the client, not a service}. There is no scheduler process, no head node and no
master anywhere. A machine acts as submitter and worker simultaneously, and the
same binary does both. A new participant runs \texttt{pipedpeer connect} with
the one-line code another member's \texttt{pipedpeer invite} printed; on the same
network the machines also find each other unaided. Across networks they meet
through an \textbf{introducer}, an address book that tells machines where to find
each other and carries no job data. Every daemon is an introducer for its own
cluster, so the role is no longer asymmetric; two optional roles are:
\texttt{pool-only} (a phone without Nix, which takes parallel chunks with
Termux's Python; a phone with Nix advertises \texttt{chunks-only} and takes them
from a Nix environment) and
\texttt{introducer-only} (a hosted server that runs nothing).

\begin{enumerate}[leftmargin=*]
  \item The user runs \texttt{pipedpeer run script.py}.
  \item The client scans imports and builds a Nix closure locally, then

  \item It asks its own daemon for the list of healthy peers, which includes
  peers on other networks, reached through local forwarders onto direct links.
  \item The coordinator filters and scores them and sends \texttt{accept} to the
  best candidate, which checks its capacity and reserves it.
  \item On acceptance the client sends \texttt{commit}, which turns the
  reservation into a running lease.

\section{Node Discovery on a Local Network}
\label{sec:discovery}

Three sources feed one table, and none blocks the others.

\textbf{UDP probes.} The daemon opens two sockets on UDP port \texttt{4242}, one
joined to multicast group \texttt{239.255.0.99} and one bound for broadcast,
both with \texttt{SO\_REUSEADDR} and \texttt{SO\_REUSEPORT}. The probe is a
fixed magic string and the reply carries a JSON node descriptor. The multicast
socket exists for a specific reason: a UDP broadcast to a shared port is
delivered by the kernel to only one socket, so two daemons on the same host
would never see each other. Multicast with port reuse reaches all of them.

This mechanism was described as mDNS in earlier documentation of this project,
and the dashboard labelled it so. It is not: there is no DNS-SD, no service
record and no conflict resolution. It is a bare request-response probe, and the
dashboard now labels it ``broadcast''.

\textbf{TCP fallback.} Access points with client isolation drop broadcast
traffic without error. When the UDP probe returns nothing, the daemon sweeps
each local interface's prefix (container and VPN interfaces skipped) with
concurrent health probes, 64 at a time with a 700\,ms timeout each, and stops
issuing probes once any daemon answers. A reply's host is taken from the
packet's source address, not from the address the peer advertised when its
daemon started, which a moved peer never corrected.

\textbf{The address book.} The node store keeps every node under its node id,
the fingerprint of its key, and every \emph{path} to it: its kind (LAN,
internet, gossip, self), host, port, when it was last seen, last worked and last
failed. A sighting only adds a candidate. A path becomes the active one only
after the poller has reached it and the certificate's key matched the node id,
and an active path that still answers is kept; a verified LAN path beats a
verified internet path. Before this, the store held one address per node and
every source overwrote it: in a container experiment LAN discovery replaced a
working internet link with an unreachable LAN address, and on two real laptops a peer
that changed network stayed at its old address until each machine re-joined by
hand. Members also gossip their own addresses, signed with their node keys,
over the token-protected API; a gossiped address is a candidate, never a fact.

\textbf{Freshness.} The poller runs every 10\,s with a 3\,s timeout and tries
the active path first, then the other candidates. A node with no verified path
for 15 minutes is removed, a node that was only ever sighted after 2 minutes;
LAN paths unseen for 10 minutes and internet paths unseen for an hour are
dropped. A sighting alone never refreshes a node, so a machine that was
discovered but never joined no longer lingers as an unknown row.

\section{Joining Across Networks}
\label{sec:nat}

A broadcast cannot leave the local network, and a machine behind another router
will not accept an inbound connection. Figure~\ref{fig:nat} shows how two such
machines come to share a direct, encrypted link without either of them opening a
port by hand and without any machine relaying their traffic.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{\figpath{fig_4.1_nat_traversal.png}}
    \caption{Joining across networks. The introducer exchanges candidate
    addresses and forwards one punch request; the two nodes then race their
    candidate pairs over a single UDP socket, fall back to a birthday collision
    when one NAT allocates a port per destination, and carry everything over a
    mutually authenticated QUIC link exposed locally as an ordinary node.}
    \label{fig:nat}
\end{figure}

\textbf{One command per machine.} \texttt{pipedpeer invite} prints a single
line, \texttt{pipedpeer connect <code>}, where the code carries the cluster
secret and up to six introducer addresses with a checksum, so a mistyped code is
refused as damaged rather than tried. \texttt{connect} saves both, restarts the
daemon once, waits up to a minute, and ends with one of three plain results:
connected, naming the machines (exit 0); partly connected, giving each missing
machine's reason and fix (exit 2); or failed --- damaged code, no introducer
answered, or secret refused --- with what to do (exit 1). The daemon reads its
configuration itself, so a daemon restarted after a reboot rejoins.

\textbf{Introducers in every daemon.} Every daemon holding a secret serves the
introducer for its own cluster on UDP 4244 and refuses other clusters. A node
registers with every introducer it knows --- those in its invite code and
members it has verified, at most eight --- every 30\,s and at once when its own
address changes, and keeps each one's last reply and last error, which
\texttt{status} and \texttt{doctor} show. With one standalone introducer, as
before, a change of that machine's IP left the cluster unable to recover and
said nothing about why. A public server can join as an introducer that takes no
jobs. Nodes register
their candidate addresses under a cluster identifier derived from the shared
secret by hashing, so the introducer never holds the secret itself. A
\texttt{connect} request causes it to forward a single punch datagram to the
target, carrying only the candidates the caller itself registered; requests are
rate-limited per source to four per second. It carries no job data. Measured over
a whole verification run, the introducer's host sent 0.2\,MB while about thirty
megabytes crossed between the peers. The address a probe arrived from is
reported in the manner of STUN \cite{rfc8489}.

\textbf{Candidates.} Each node offers three kinds of address: its LAN addresses;
a port its router agreed to forward, requested by PCP \cite{rfc6887}, NAT-PMP
\cite{rfc6886} or UPnP-IGD \cite{upnpigd} for two hours and renewed at half the
lifetime actually granted; and the reflexive address the introducer observed. A
router mapping is withheld when its external IP address differs from the
reflexive one (once the reflexive address is known; on the very first poll it is
not yet, and the mapping is published unchecked). Behind a second layer of NAT, such as a phone tether, the router that
answers is not the one facing the internet, and publishing its mapping would
advertise an address nobody can reach.

\textbf{One socket.} Punch probes, introducer messages and QUIC share a single
UDP socket on port 4243. This is the mechanism, not a convenience: a router's
mapping belongs to the socket that created it \cite{ford2005p2p}, so the
connection must arrive on the socket the probes left from. Incoming datagrams are
separated by content --- probes by four magic bytes, introducer messages by a
leading brace, everything else handed to QUIC.

\textbf{The race.} Both sides probe every pairing of their candidates every
250\,ms for a fifteen-second window, rather than trying candidates one at a time,
which would add a timeout for every address that cannot work. When one side's
NAT allocates a fresh external port for every destination there is no address to
publish, and an ordinary punch fails: on a phone tether the project's own laptop
was seen as port 38471 by one reflector and 27486 by the next, and a punch moved
400 packets each way without any arriving. For that pair the \textbf{birthday
collision} \cite{anderson2020nat} runs: the side with the port-per-destination NAT opens 256 sockets
toward the peer, the other sends 600 probes to random ports, and the socket that
is hit is the one kept, since its mapping is the reachable one.

\textbf{The link.} The winning path carries QUIC \cite{rfc9000} with TLS~1.3.
Inside it each side sends a hello signed with its Ed25519 node key, and each
checks that the key's fingerprint is the node it meant to reach and that the
cluster identifier matches. TLS on this link skips certificate checks, so a
node's identity rests on the hello. The hello therefore signs the session's
exported keying material \cite{rfc5705} and proves the cluster secret with an
HMAC \cite{rfc2104} over the same value, so it is valid for one session and one cluster only;
an earlier hello, which signed only the cluster and a nonce the signer chose,
could be replayed by a peer to a third node to pass as its sender. A node on an
older build is refused and told why. The link is then exposed to the rest of the daemon
as a TCP forwarder on a loopback port, recorded as that node's internet path; each
local connection becomes one QUIC stream to the peer's daemon. Placement, closure
transfer and gradient exchange therefore work over the link unchanged.
\texttt{pipedpeer status} reports how each peer is reached: \texttt{self},
\texttt{lan} or \texttt{internet}.

\textbf{Roaming.} A peer that changed IP used to return only after about three
minutes, because the other side kept the dead link and refused the new one as
already connected. A hello from a key that already has a link now replaces that
link at once. The daemon checks its interfaces every 5\,s; on a change it
migrates the QUIC connections it dialled to the new address, redials those it
accepted, and registers again with every introducer.

\textbf{No relay.} A relay was built and then removed from the data path,
because a relay carries every byte of every job and becomes the cluster's
bottleneck and its cost. A peer with no direct path is logged with the reason,
never offered to the scheduler, and retried after a back-off; \texttt{pipedpeer
status} lists it under the table with that reason. A live link does not depend on
the introducer: with the introducer suspended, a peer was reached in 0.03\,s.

\textbf{What a NAT lab found.} Until a container lab with real translators
existed (Section~\ref{sec:workloads}), punching was exercised only between real
machines by hand. The lab showed peers behind NAT rarely linking, for four reasons,
all since fixed. The socket a birthday collision found listened under the
search's context, which ended on adoption, so the peer's dial met a closed
listener; it now accepts dials for 30\,s and stays open while any link it
accepted lives. The same socket kept the search's read deadline, so after
adoption every read failed and its links died about 90\,s later; the deadline is
now cleared. A node registered before it knew its public address, so a woken
peer punched at a private address on another network; it now registers again as
soon as it learns that address, before asking anyone to punch. And the race
returned an IPv4-mapped address that never matched a candidate, so an ordinary
punch was labelled a collision.

\section{Security and Identity}
\label{sec:trust}

The design documented previously assumed a trusted local network and had no
authentication of any kind. The current design has three layers
(Figure~\ref{fig:trust}), each described here together with what it does not
cover.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{\figpath{fig_4.2_trust.png}}
    \caption{The three layers of trust: a shared secret on every API route,
    pinned TLS (or QUIC across networks) on the wire, and the node key that both
    authenticates links and signs closures.}
    \label{fig:trust}
\end{figure}

\textbf{The shared secret.} The first machine's set-up stores 32 random bytes,
readable only by the user, before its daemon first starts; \texttt{connect}
stores the secret from the invite code. Every route on the daemon,
\texttt{/health} included, then requires it, compared in constant time; outbound
requests carry it automatically. Jobs receive it in their environment so that
the shim can reach its own daemon, which means a job's code can read it. The
web page receives it in the URL fragment opened by \texttt{pipedpeer ui}, which a
browser never sends to a server; loopback is not exempt, since peers across
networks arrive through loopback forwarders. The secret is attached only to a host that has proved it holds it:
a remote host is first challenged and must return an HMAC over the challenge,
whereas the LAN sweep once sent the secret in plain HTTP to every host on the
subnet that answered on the port.

\textbf{Pinned TLS.} Each daemon's self-signed certificate is made from its
Ed25519 node key. TLS and plain HTTP share the daemon port; the listener inspects the first
byte of each connection and treats a TLS handshake record as TLS. Clients try
TLS first, and the pin is keyed by node id rather than by address: a
certificate whose key matches the expected node id is accepted wherever the node
now is, and a different key for a known node id is refused. Pins keyed by
address used to refuse a new machine that happened to get an old peer's IP. The scheme is trust on first
use, and it is opportunistic: a handshake that fails for any reason other than a
pin mismatch makes the client remember that peer as plain HTTP. The code records
that an attacker able to break the handshake can therefore force plain text.
Peers across networks are reached through loopback forwarders, so their traffic
is encrypted by QUIC rather than by this layer.

\textbf{Node keys and signed closures.} Each node holds an Ed25519 key
\cite{bernstein2012ed25519} whose fingerprint is its node id everywhere. There
used to be three identities --- a random identifier in the node store, the key's
fingerprint on links, a separate TLS key --- and the mismatch produced duplicate
rows for internet peers. The same key authenticates QUIC links, makes the TLS
certificate, signs gossiped addresses and signs closures as a Nix signing key. Nodes publish the public half in their heartbeat,
each daemon keeps a list of the keys of the nodes it knows, and \texttt{setup}
adds those keys to the system Nix configuration as additional trusted keys, with
consent. It never disables Nix's signature requirement; an earlier version did,
switching off signature checking for everything the machine installed so that
one program could receive unsigned closures. A closure sent between daemons in
the signed format is imported under the receiver's own signature policy. On a
machine with signatures required, a closure signed by a trusted peer imported and
ran, and the same closure was refused once the sender's key was removed from the
list.

\textbf{Getting peer keys to Nix.} On a fresh cluster the first job never left
its submitter: every worker refused the closure as lacking a trusted signature,
because the worker knew the sender's key only in its own list and Nix trusts
only what its configuration names. Three changes close this without relaxing
the signature requirement. The import passes the cluster's keys to that one copy
operation. An archive names its signer and key, which the receiver checks
against the signer's published identity before trusting it for that import, so
a job sent right after joining is not refused for want of a poll. And because a
multi-user Nix daemon ignores keys passed by a user it does not trust, set-up
installs, with the one privileged step it already needs, a root-owned copy of
the binary and a rule letting the user run only that file; run under that name,
the binary does nothing but add or remove keys of the cluster's fixed form, each
in its own configuration include, and restarts the Nix daemon. The daemon calls
it for a key system Nix does not yet trust, before importing, and retries a
failure every 15 minutes. A refused import is reported to the submitter.

\textbf{What remains uncovered.} The secret is one per cluster, so there is no
per-user or per-node authorisation, and every holder can run code on every node.
The trusted-key list is built from every node in the node store, including nodes
found by unauthenticated LAN discovery, so a key in that list is not bound to an
authenticated identity. With the key helper installed, anyone holding the
cluster secret can get signed paths trusted by system Nix on every machine with
no human involved, as was already true after a manual trust step. The older
closure format, which a submitter still uses for its own upload, is imported
without a signature check. LAN discovery is unauthenticated, though its answers
are only candidates. Section~\ref{sec:security} returns to these.

\section{Placement and Scoring}
\label{sec:placement}

Candidates are merged from the node store, live discovery and the local node,
deduplicated by node identifier; a node with a role is never offered a job. Five hard filters then run
in order: architecture must match the closure; a GPU must be present if one was
required; and free memory, free cores and free VRAM must each satisfy the
request. Every rejection records a reason, which surfaces in
\texttt{pipedpeer jobs <id> --explain}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.3_placement_flow.png}}
    \caption{Placement: gather, filter, score, lease, retry. A task is never
    dropped; when nothing is eligible it is queued and retried.}
    \label{fig:placement}
\end{figure}

Survivors are scored. Writing $u_{\text{cpu}}$ and $u_{\text{mem}}$ for CPU and
memory utilisation in percent, $n_{\text{jobs}}$ for the count of running jobs,
and $\hat{c}, \hat{f}, \hat{m}, \hat{r}$ for the core count, clock speed, free
memory and free-core ratio each normalised onto $[0,1]$ against a saturation
point:

\begin{equation}
\label{eq:score}
S = \Bigl(1 - \tfrac{u_{\text{cpu}}}{200} - \tfrac{u_{\text{mem}}}{200}
    - 0.05\,n_{\text{jobs}}
    + 0.10(\hat{c}-\tfrac12) + 0.06(\hat{f}-\tfrac12)
    + 0.10(\hat{m}-\tfrac12) + 0.10(\hat{r}-\tfrac12)\Bigr)\cdot H
\end{equation}

where $H$ is the node's health score. Two properties matter more than the
individual coefficients.

\textbf{Load dominates hardware.} The two load terms can subtract $1.0$ between
them, while the four hardware terms together move the score by at most $0.36$.
A fast but busy machine therefore loses to a slower idle one, which is the
intended behaviour on a network of workstations that people are also using.

\textbf{Missing telemetry is neutral.} The normalisation returns $0.5$, the
midpoint, for a value that is absent or non-positive, so a node that does not
report its clock speed is neither rewarded nor punished. This is what makes the
function safe across heterogeneous machines whose telemetry is uneven.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.4_scoring_weights.png}}
    \caption{Left: the range each term can contribute. Right: the same function
    applied to an idle strong node and a loaded weak one.}
    \label{fig:scoring}
\end{figure}

When a GPU is requested, a second function contributes up to $0.8$ more, drawn
from total VRAM, device count, free VRAM on the best device and compute
capability, less a utilisation penalty.

The scoring function is unchanged from the version documented in August 2026.
What changed is the memory figure it reads: a node now advertises the memory it
can actually \emph{grant} --- its own budget less the reservations of every
daemon on the same machine --- rather than the machine's free memory
(Section~\ref{sec:sandbox}).

Within one run, placement also learns. A node that refuses the job's signed
closure is left out for the rest of the run, and the client prints the command
that fixes it on that node; a refusal is that node's missing trust, not every
node's, so the run fails only when no node is left. The submitting machine's
own memory ceiling is read once per run from its daemon instead of being
unknown. A run sent away with \texttt{-{}-remote} now waits up to ten minutes
for a node with room, rather than fifteen seconds, and every 30 seconds says why
each node is busy; a job that could never fit any node still fails at once.

\section{The Lease Protocol}
\label{sec:lease}

Placement is a three-phase handshake, and its state machine is where crash
recovery lives.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.5_lease_fsm.png}}
    \caption{Lease states. Recovery is a consequence of expiry rather than a
    separate mechanism.}
    \label{fig:lease}
\end{figure}

An \texttt{accept} reserves capacity for 30 seconds with a 5 second grace
period; a \texttt{commit} promotes the reservation to running, renewed every 30
seconds and reaped after 5 minutes without renewal; \texttt{complete} releases
it. A sweeper runs every 2 seconds.

Renewal used to be the submitter's job on only one of its two paths. The
coordinator's remote path renewed and dropped every failed renewal silently;
the plain run path --- the local default and \texttt{-{}-host} --- committed its
lease and never renewed it. An environment build plus upload longer than the
5 minute expiry let the node reap the lease, and the job then ran bound to
nothing. Both paths now renew every 30 seconds with a 10 second timeout while
the environment builds and uploads; failures show with \texttt{-v}, and a
fourth in a row warns without it. As a backstop the node binds a job that names
an expired lease to a fresh lease with no memory or GPU reservation, and logs a
warning. In the lab, with one node held to 800\,kbit/s, a 533\,s environment
build ran with no expired lease and the lease was released when the job ended.

Two details carry the correctness argument. First, the concurrency and memory
checks and the lease insertion happen \textbf{under a single lock}, so two
submitters racing for the last slot cannot both succeed (the cores check runs
just before the lock is taken). Second, the concurrency limit counts
reserved and running leases together, deliberately, so a burst of submitters
cannot slip through the window between accept and commit. Admission checks cores,
then the concurrency limit, then memory against the daemon's budget, then GPU
devices.

Recovery then needs no additional machinery. A submitter that dies stops
renewing and the sweeper reclaims its slot. A worker that dies stops answering
health checks, is marked unreachable at the next failed poll, and its in-flight
connection fails, which the coordinator treats as a failed attempt and
reschedules elsewhere, with back-off doubling from 2 seconds to a 2 minute
ceiling. Waiting for room never drops a task, but a job that \emph{fails} is run
at most three times, on nodes not yet tried first, and then returns its last
error; it used to retry a killed or sandbox-failed job forever.

Deciding that a worker has died is less simple than it looks, because from the
submitter a dead node and a lost network look the same: the connection drops.
The first means run the job elsewhere, the second means detach and wait.
The client used to ask only another peer, so with two machines a silent node
always looked like the submitter being offline and the job was never rerun. It
now runs three probes at once, two seconds each and none needing root: another
peer's health endpoint, a registration with the introducer, and a TCP connection
to the default gateway on a common port, where an accepted or a refused
connection both count. If any answers, the node is the one gone. In the lab,
with two machines, the client named the node gone 16\,s after it was killed.

\section{Reproducing the Environment}
\label{sec:env}

\textbf{Import scanning.} The client extracts imports with a hand-written,
line-oriented parser rather than a full parse of the program. It strips
comments, takes the module from \texttt{from X import \ldots}, and splits
\texttt{import a, b as c} into every module named; the earlier version used a
single regular expression that kept only the first. Being line-oriented, it does
not see an import split across continuation lines or performed through
\texttt{\_\_import\_\_} or \texttt{importlib}, and it can pick up import-like
text inside a multi-line string. Each name is then classified as a local file, a
standard library module (from a list of 124), or an external dependency, and
external names are resolved through a 40-entry mapping table that handles cases
such as \texttt{sklearn} to \texttt{scikit-learn}.

\textbf{Imports outside the table.} Until October a third-party import absent
from that table resolved to nothing and was silently omitted from the closure,
so the job died on an import error on the node. Such an import is now looked up
as the attribute of the same name in the pinned package set's Python packages,
with one evaluation for all of them, and added when it exists. Only what is
still missing is reported, before anything runs, with the flag that would add
it; a failed evaluation says so and falls back to the warning. A
\texttt{requirements.txt} beside the script is read as if it had been passed
with \texttt{-{}-pkg}. The scan also follows the script's own modules: a helper
module's imports used to go unread, so a helper importing a plotting library
left the environment without it. Each local module is now scanned against its
own directory and then the script's, with a visited set so that import cycles
end. A \texttt{uv.lock} file, which replaces detection entirely when present,
and an explicit \texttt{-{}-pkg} flag remain the escape hatches.

\textbf{Common packages built ahead of time.} There is no layered base
environment; what environments share is Nix's own store paths, and a transfer
sends only the paths a peer lacks (Section~\ref{sec:cache}). A preparation
step uses that: it builds one environment importing the usual scientific set
(numpy, pandas, scikit-learn, scipy, matplotlib, seaborn, tqdm and CUDA torch)
on every machine through the dry run of Section~\ref{sec:observe}, so a script
seen for the first time shares those paths and fetches only what it adds. A
teacher-style script's environment took \textbf{54}\,s to build without that
step and \textbf{4}\,s with it, measured on a container of the laboratory-layout lab
(Section~\ref{sec:res-lablayout}).
% evidence v1/15-pc3-pkgprep-before-after.txt (8e14b9b): dry-run environment build, before/after prep-4-common

\textbf{The keystone.} Nix \cite{dolstra2004nix} names every build output by a
hash of its inputs. The generated flake pins an \emph{exact} nixpkgs
revision, not a branch. The reasoning is the foundation of the entire caching
layer. A branch resolves at build time, so two nodes building the same script on
different days would produce different store paths; because the cache is keyed
on the store path, the system would then re-ship a multi-hundred-megabyte
archive for every job. Pinning an exact revision makes the store path a stable,
content-derived name for an environment, identical across every machine and
across time. Section~\ref{sec:res-cache} measures what that buys.

Every generated environment also contains \texttt{cloudpickle} \cite{cloudpickle}, so that parallel
kernels with no source can be shipped by value (Section~\ref{sec:intercept}).
Two deliberate exceptions to the package set exist, both restricted to x86\_64
Linux: scikit-learn is pinned to a specific wheel because the package set lags
the version targeted, and torch with CUDA is fetched as a pinned wheel set inside
a \emph{fixed-output derivation} with a recorded hash, because building it from
source takes hours. The CUDA build is used only when a GPU is requested ---
which is the default when a script imports torch, unless \texttt{-{}-gpu off}
--- and otherwise the package set's CPU build is used.

\section{Closure Transfer and Cache Reuse}
\label{sec:cache}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.6_closure_cache.png}}
    \caption{The store path is the cluster-wide cache key. Most submissions ship
    no environment at all, and a related environment ships only the store paths
    the receiver lacks.}
    \label{fig:closure}
\end{figure}

Before uploading, the client asks the target whether it can already run the
closure. Only on a negative answer does anything cross the wire, and then, where
possible, only part of it.

There are in fact \textbf{two different questions} a node can be asked, and both
are needed. The first is whether the archive is in its cache. The second is
whether the closure is \emph{materialised}, that is, whether its entry point
exists on disk. A deployment with a shared store volume has the closure present
without ever having cached an archive, so re-sending to it is wasted work; on a
per-node store the entry point appears only after a real import. Either
predicate alone is wrong for one of the two layouts.

\textbf{Path-level difference.} A closure is a set of store paths, and two
environments that differ by one package share most of them. The client lists the
closure's paths and asks the target which it lacks; if some but not all are
missing, only those are sent, as a partial import that the receiver never caches
as the whole closure. Adding one package to an environment a peer already held
sent 7 of 43 paths, 206.0\,MB reduced to 28.6\,MB; adding \texttt{cloudpickle}
to every environment cost a peer 3 of 39 paths, 0.43\,MiB of a 444\,MiB closure.

\textbf{Signed transfer between daemons.} After an upload, the worker pushes the
closure to peers that cannot yet run it. This is not merely an optimisation:
parallel work is only ever spilled to peers that can run the closure, so the push
is what makes the cluster usable for the distribution described in
Section~\ref{sec:intercept}. A peer that advertises the signed format receives
one archive containing a signed binary cache --- the signature records for every
path and the compressed archives for the paths it lacks --- produced by Nix's own
copy mechanism and imported the same way, so the receiver's signature policy
applies. Other peers receive the older unsigned export, which is also what a
submitter uses for its own upload.

\textbf{Not waiting for the slowest peer.} The push used to run inside the
upload handler and wait for every peer's send, under a 10 minute client
timeout, so a run started only when its slowest peer had imported the
closure. The upload now waits at most 60 seconds. A peer still importing
finishes in the background with a warning and joins the pool by itself, since
each parallel chunk asks afresh which peers can run it; meanwhile the peer's
store reports ``importing'', so other nodes do not start a second send to it,
and two sends of the same closure to one peer are shared. A background send
is cut only when it stops moving: after 60 seconds with no bytes sent, or 10
minutes after the full body if the peer never answers, instead of after 10
minutes in total, which a large closure on a slow link exceeded on every run.
A restarted send asks again which paths are missing, so it skips what already
arrived. In a lab of two 768\,MiB nodes with the second held to
800\,kbit/s, a cold run fell from 1000.9\,s to 137.5\,s (the environment send
from 641\,s to 60.1\,s), a warm run from 603.7\,s to 62.4\,s, and a later run
took 2.1\,s with the slow node taking 23 of 64 items; the one background send
took 898.9\,s, longer than the old limit allowed. The times before the fix are
bounded by the 600\,s timeout (measured before the fix); the times after it
are from an idle host.

A fresh peer can also fetch from the public binary cache the paths it lacks
instead of taking them from the sender over the local network. That import
used to wait on the download without limit; it now waits at most 30 seconds
once the sender's archive is in, then cancels the download, skips the cache
for 30 minutes and answers so that the sender sends every missing path
itself.

\textbf{Bounded caches.} Both closure caches are pruned least-recently-used to a
cap of 8\,GiB each by default, after every send and at daemon start. With the cap
lowered to 50\,MiB, the caches on one node went from 109\,MiB to 28\,MiB and from
768\,MiB to 4\,KiB, and the next job still ran on its peer, since what was
evicted is derived data and was rebuilt. Workspace archives above 1\,MiB and all
results archives are compressed with Zstandard \cite{rfc8878}; readers recognise
Zstandard, gzip or plain archives by their leading bytes.

\textbf{A transfer that can be seen.} The client times packing the closure and
sending it; on a terminal the send draws a progress bar, and otherwise it prints
one line with the paths, bytes and time. A flag, \texttt{-{}-cold}, sends the
whole closure as if the node had none, skipping both questions and the path
difference, so that a first run can be timed on a warm cluster. It cannot undo
the submitter's own build or the node's earlier import, and the run summary
marks such a send as cold; true first-run cost therefore comes from fresh
machines. A signature refusal on import is no longer swallowed: the upload
returns it and the client prints why the peer took no work.

\section{Execution and Isolation}
\label{sec:sandbox}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.7_sandbox.png}}
    \caption{What the job can and cannot see. The absences are as deliberate as
    the mounts. Shared memory is mounted world-writable because Python's
    \texttt{multiprocessing} requires it, and the driver libraries are bound
    file by file so that the host C library cannot shadow the closure's.}
    \label{fig:sandbox}
\end{figure}

Jobs run under \texttt{crun} \cite{crun} in an OCI bundle \cite{oci2021} with a minimal read-only root: the
store read-only, the workspace read-write, a private home, and temporary
filesystems for scratch space. Shared memory
is mounted world-writable specifically because Python's
\texttt{multiprocessing} maps POSIX shared memory for its semaphores and fails
without it.

GPU support mounts the device nodes and then binds the driver libraries
\emph{file by file} rather than binding the host library directory, because
binding the directory would place the host C library ahead of the closure's on
the search path. Without this, torch silently falls back to the CPU, which is
indistinguishable from a working run except by its speed.

\textbf{A memory ceiling for every job.} Where the daemon has a usable cgroup v2
hierarchy (otherwise it logs once that jobs run without an enforced limit),
each job runs in its own cgroup with a memory limit, and an equal swap limit, of twice its estimated requirement with a
512\,MiB floor, clamped to what the node can grant but never below what admission
approved. When the job is killed and the cgroup's out-of-memory counter has
risen, the client is told the job ran out of memory and how to raise
\texttt{-{}-mem}, rather than seeing a bare exit code. A job with no estimate
used to run with no limit at all; it is now capped at 4\,GiB, with a note
pointing to \texttt{-{}-mem}, and the node still lowers that to what it can
spare.

\textbf{A memory ceiling for the daemon.} Per-job limits covered only sandboxed
jobs; parallel chunks run in warm worker processes in the daemon's own cgroup,
and a pool benchmark on a development machine once drove it into a global
out-of-memory condition in which the kernel killed an unrelated process.
\texttt{pipedpeer start} therefore launches the daemon in a user
\texttt{systemd} scope with a memory ceiling of half the machine and swap
refused, where a user \texttt{systemd} is available. A daemon without one, such
as one in a container, runs a watchdog instead: every second it sums the memory
of the daemon's children and, past half the machine or the configured ceiling,
kills the largest child and logs it, never the daemon. It stands down where a
cgroup already sets a limit, and an allocation fast enough to outrun a
one-second poll is not caught. A softer throttling limit was rejected on measurement: a 3\,GiB
allocation under a 1\,GiB soft limit stalled at 998\,MiB with 7,381 throttling
events and no progress for minutes, which is worse than a failed job. Daemons on
one machine, recognised by the kernel's boot identifier, subtract one another's
reservations, so two of them cannot promise the same memory twice; on one
machine with a host daemon and a container worker this changed the total promised
from 7.24\,GiB plus an unbounded daemon to 6.74\,GiB and 1.97\,GiB.

\textbf{Without root.} On a machine with no system Nix, set-up seeds a private
store in the user's data directory and mounts it at \texttt{/nix} inside a user
and mount namespace; \texttt{crun} is installed into the user's own binary
directory when no package manager supplies it; and working files live under the
user's state and cache directories rather than a RAM-backed temporary directory.

\textbf{What the sandbox does not do.} The job runs as user 0 inside the
container and shares the host's network: there is no network namespace. The
specification sets no seccomp filter and no capability list. The namespaces in
use are process, IPC and mount, plus hostname where the kernel allows it; when
\texttt{crun} runs without root it adds a user namespace itself. Isolation is the
default but not mandatory: the \texttt{python} shorthand turns it off, and a node
without \texttt{crun} or user namespaces warns and runs the job unisolated ---
unless it uses a private Nix store, in which case it refuses.

Results are diffed rather than copied wholesale. Only files created or modified
during the run are returned, with deletions carried in a manifest, so a job
cannot overwrite the submitter's own sources. On extraction the submitter
refuses any path that escapes its directory, and the worker skips such paths in
an incoming workspace.

\textbf{Output as it is written.} The daemon used to split a job's output into
lines, so a progress bar that redraws one line with a carriage return showed
only its final state. It now forwards each read of up to 4\,KB unchanged,
carrying an incomplete trailing UTF-8 character into the next chunk, and the
submitter prints the bytes as they arrive, so a progress bar on a remote node
animates on the submitter's terminal.

\textbf{Stopping a job.} Until October nothing could stop a running job: the
daemon never watched its client, and an interrupt left the script, its parallel
chunks on peers and every training rank running. An interrupt, a termination
signal or a closed terminal now makes the client send one cancel frame on the
execution channel. The daemon signals the job's process group, or asks
\texttt{crun} to, and kills it two seconds later if it is still alive; the final
frame records the cancellation. The cancel reaches remote runs, \texttt{map} and
every training rank. Chunks that a killed script had asked for stop as well:
each carries its request's context, so when the request ends the local workers
are killed by process group and forwards to peers are dropped, with nothing
re-run. The coordinator records the lease as cancelled and does not retry. A
connection that ends \emph{without} a cancel frame --- a crash, a lost network,
a detach --- never kills the job, which is what background mode builds on. In
the laboratory-layout lab (containers on one laptop), peers stopped within \textbf{2}\,s of
the interrupt: their pool counters showed the cancel at the next 1.3\,s sample.
% evidence v1/31-ctrlc-poolwatch.txt (8e14b9b)
The interrupt now also stops the submitter's own Nix work. Exporting and packing
the closure ran with no context, so Nix kept packing a multi-gigabyte closure
until the client exited. Nix now runs in its own process group, which on cancel
receives a termination signal and, five seconds later, a kill. The gentler
signal comes first because a private store runs Nix inside \texttt{crun} in its
own session: \texttt{crun} forwards it, while killing \texttt{crun} outright
would leave Nix running.

\textbf{Background mode.} The daemon keeps every frame of a job's output in a
log in the job's directory, in the order a live client saw it. A detach flag,
or the suspend key during a foreground run, closes the channel normally without
a cancel frame; the client prints the job's short identifier and the command to
reattach, and the prompt returns. \texttt{pipedpeer attach} replays the log,
follows live without gaps or repeats, downloads the results at the end and
prints the run summary; an interrupt during attach cancels the job. Two
invariants make this safe. A lease follows its job: the execution request
carries the lease identifier, and the sweeper keeps a lease bound to a running
job past its expiry without renewals, because a detached or crashed submitter
renews nothing, so a node's admission never thinks a busy slot free. And a
detached job's directory is pruned 24 hours after it ends, while its output log
is capped at 50\,MB, keeping its newest half behind a note of what was dropped
and never the final frame, so a job that prints without end cannot fill a disk.
A job still marked running when its daemon starts is failed with a final frame
saying the daemon restarted, so an attach ends rather than waits. A remote job
survives its submitter vanishing and can be attached when the submitter
returns; a parallel script cannot, because it runs on the submitter. Detach is
offered for single runs, not for training rings or \texttt{map}.

\section{Transparent Interception}
\label{sec:intercept}

This is the system's distinguishing feature.

\textbf{Delivery.} The shim is a Python file of 3,822 lines embedded in the binary. It is
appended to the workspace archive under a hidden directory using an archive
transform, so the user's project on disk is never modified, and the worker
points the interpreter's module path at that directory. CPython imports it
automatically before the user's first line. Nothing is installed on any node.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.8_shim_injection.png}}
    \caption{How the shim reaches the interpreter and what it replaces.}
    \label{fig:shim}
\end{figure}

\textbf{A hazard worth recording.} Nix ships its own module of the same name,
and only the first on the path is imported. The shim would therefore suppress
the one that adds the environment's package directories, and every import in the
closure would fail. The shim replays that work explicitly before doing anything
else.

\textbf{Patching is deferred.} \texttt{multiprocessing.Pool} and
\texttt{ProcessPoolExecutor} are patched at start-up; NumPy, pandas, torch and
joblib are patched on their first import, through an import hook, rather than
when the shim installs itself. This matters: importing torch costs roughly
1.7 seconds, and paying it up front charged that cost to every job whether or
not it used torch. Section~\ref{sec:res-shim} measures the difference.

\textbf{Parallel maps in detail.} \texttt{map}, \texttt{starmap}, \texttt{imap}
and \texttt{imap\_unordered} go to the cluster (\texttt{imap} lazily, in
batches; \texttt{imap\_unordered} currently returns results in order), while
\texttt{apply} and \texttt{apply\_async} stay local. The local pool's width is
chosen from free memory and cgroup headroom, and the width the user asked for is
ignored unless \texttt{PIPEDPEER\_RESPECT\_POOL\_SIZE=1}. A head of items runs
locally first to measure the cost of one item, and a map whose remaining work
is under half a second stays local. The kernel then has to reach the peer, and
there are two ways for it to do so. A plain module-level function --- including
one defined in the script's \texttt{\_\_main\_\_}, which the earlier design
could not ship at all --- travels as its \emph{source}, with the helper functions
it calls and a pickle of the module data it reads. A lambda, closure, bound
method, partial or decorated function, which has no source to send, travels
\emph{by value} through \texttt{cloudpickle}. Anything neither can carry, such as
a function holding an open file, is counted as unshippable and runs locally.
Every run can write a \textbf{receipt} counting the items that ran remotely and
locally, the parts that failed, the calls that could not be shipped, and the
node each part ran on, so that a claim about where work ran can be checked
rather than inferred.

\textbf{Sharing work by measured speed.} On the daemon, a chunk is divided among
peers by a makespan solver. Each device is modelled as a set-up time plus a
throughput, fitted by least squares from the last eight parts it returned; an
unmeasured peer is assumed to be as fast as this node, scaled by its core
count, since assuming it slow would size its share below anything worth sending
and it would never be measured. The solver finds the finishing time $T$ at which
the devices together complete the work, allocating each $(T - o_i)\,r_i$ items
for set-up time $o_i$ and rate $r_i$, and drops any device whose set-up time
alone exceeds $T$: it ``cannot start before the rest of the cluster finishes''.
A chunk posted by a shim on the same machine keeps no local share, because the
local pool is already using those cores, and on a peer a chunk fans out across
its cores. On a lab cluster limited to 8, 2 and 1 CPUs, dividing by headcount
ran 1.6 times slower than not distributing at all; dividing by measured
throughput declined the one-CPU worker and took a median of 2.87\,s against
3.61\,s by headcount.

A peer that runs past its five-minute budget for a part is no longer written
off. It used to be marked dead and its part restarted locally from scratch,
discarding however far it had got; now the peer's copy keeps running, the same
part starts locally, the first to finish is used, and the loser is cancelled. If
both fail, the part fails with both errors.

\textbf{Learning a slow peer.} The fit used to learn a peer's speed only from
parts that peer finished first. A slow peer's parts always lost the race to a
backup copy or to the script, so it kept a fast estimate, received a share of
every chunk sized for a fast machine, and, since each reply waits for all its
parts, the run took about as long as one node alone. A part still unfinished
past its prediction now counts as taking at least that long, which can only make
an estimate slower. Within the first run, three further rules act before the fit
has caught up: a split part waiting for its peer starts on another peer with a
free slot when that would finish sooner; a part running past its prediction
gets a copy on the fastest free peer, the first result winning; and a chunk too
small to split goes to the peer predicted to finish first. In the lab, with one
peer held to a tenth of the processor against a cluster of equal peers, four
consecutive runs took 1.60, 1.25, 1.09 and 1.08 times the equal cluster's time,
where they had taken 2.11, 1.35, 1.37 and 1.31 times; equal clusters were
unchanged (ratios from a host loaded to 19--21). Most of the first
run's remaining gap is starting pool workers on fresh daemons.

\textbf{Keeping the sender free.} Sending a script away does not by itself keep
the sending machine idle: its node may spread pieces back to it, and a script
run locally spreads its own work there. With \texttt{-{}-offload} the script and
its sequential code still run on this machine, but every distributed piece ---
parallel-map and \texttt{joblib} chunks, pandas and NumPy work, training ranks
--- goes only to other machines, shipped without consulting the cost model.
Machines are told apart by the kernel's boot identifier rather than an address,
so every daemon on this physical machine is excluded. A piece no other machine
can take runs here with a one-line warning rather than failing the run. Because
the containers of the lab share one kernel, they count as one machine there,
and the lab cannot show this.

Interception replaces module functions, so the operator form \texttt{A @ B} is
not intercepted for NumPy arrays. pandas operations are distributed only above
512\,MB unless forced, because their arithmetic intensity is low.

\textbf{Why the shuffle is exact.} Hash partitioning on the key is the
standard technique of MapReduce \cite{dean2004mapreduce}; the choice here is to
use only that path, never a combiner. Rows are bucketed by a hash of the grouping
or join key, so equal keys always fall in the same bucket and therefore land on
the same node. Every key is complete on exactly one node, so each node's
aggregation is a \emph{complete} aggregation and the origin combines the
partials with a plain concatenation. There are no combiners, and consequently
\emph{any} aggregation specification works, including those that have no
combiner form at all. Bucket zero is kept local.

\textbf{What exactness means here.} It means exactness of \emph{values}, not of
row order. A concatenation of shuffle buckets does not reproduce pandas'
documented join ordering, which is why the join tests sort both sides before
comparing; a script that depends on the row order of a \texttt{merge} result can
therefore see a different order under interception. Grouped aggregation is
unaffected, and its tests assert frame equality directly.

\textbf{Data-parallel training without a socket mesh.} Rather than let torch
build its rank-to-rank mesh \cite{li2020pytorchddp}, which requires direct connections on its own ports
between every pair of ranks, each rank posts its gradient to the lead node's
ordinary daemon port. That works on any network where the daemon port already
works, including over the links of Section~\ref{sec:nat}, which is the only
assumption the rest of the system makes.

The daemon originally acted as a blackboard, returning every rank's gradient to
every rank for the shim to average. Measured on two machines, that made training
21 times slower than one machine: 62.9\,s against 2.9\,s, with each step's reply
carrying the whole ring. The daemon now \emph{reduces}: gradients arrive as raw
little-endian frames, are summed in double precision weighted by the number of
samples behind each, $\sum_i n_i g_i / \sum_i n_i$, and one averaged gradient is
returned. Gradients travelled in half precision by default, with an 8-bit
encoding on request; since the address-book phase 8-bit is the default, with
one scale per block of 4096 values and the rounding error carried into the next
step in both directions (error feedback) \cite{dettmers2016eightbit, seide2014onebit}. On two machines over a home link, the same training run took 54.9\,s on
one machine, 69.4\,s on two ranks in half precision with 36.2\,s spent
synchronising, and 56.1\,s on two ranks in 8-bit, with final losses of 0.087495,
0.087497 and 0.087688. On that link two machines did not beat one: half
precision was 26\% slower, and 8-bit about level for a slightly worse loss. The
run says so: each prints at exit whether the ring paid for
itself, counting distinct machines rather than ranks.

\textbf{Choosing and refitting the ring.} Ranks are chosen by measurement. Each
candidate's throughput is probed, and the ring admitted is the prefix of the
fastest that maximises $k \cdot r_k$ --- the ring's worth if every rank ran at the
slowest admitted rate --- using one device kind only, GPUs when any are wanted
and present; the lead is a GPU node whenever any candidate has one, after a CPU
lead in a real two-laptop run built a smaller model whose shape every GPU rank's
update then failed to match. Each rank's shard and batch slice are then sized by
its share, and the slices sum to the script's own batch, so the learning rate and
the mathematics are the script's; each rank used to run the full batch, which
multiplied the effective batch by the ring size at an unchanged learning rate.
Every rank also sends a manifest of its parameters (names, shapes, types) to the
opening barrier, and a mismatch stops every rank with one message. On a ring
of 16, 8 and 2 cores, admission took the 16 and the 8, shared the work 66:34, and
ran in 23.6\,s against 25.4\,s with equal batches. Every 20 synchronisations the
daemon refits the shares from the step rates actually observed, applying them at
the next epoch boundary if any share has moved by a tenth or more, and it can
drop the slowest rank --- never rank 0, never below two --- when that rank adds
more synchronisation time than computation. Throttling one rank from 8 CPUs to 1
and back moved the shares from 64:36 to 84:16 and then to 70:30. A round that a
straggler has not joined completes without it after 45 seconds.

\textbf{One GPU or a split.} In a real run, a small model split across two
laptops on Wi-Fi trained for about nine minutes, against about twenty seconds on
one GPU, because 92\% of every step was synchronisation. The ring is now kept
only when it earns its place: after a warm-up the lead daemon compares the
measured step time of the split with that of the fastest rank alone, and either
keeps the ring or releases every rank but the fastest, which exit with a code
meaning ``released'' rather than ``failed'', with one plain line in rank 0's
output. A user who names a ring size turns the decision off.

\textbf{Synchronising less often.} A second mode, \texttt{-{}-ddp-sync fast},
synchronises every $H$ steps instead of every step, in the manner of DiLoCo
\cite{douillard2023diloco} and post-local SGD \cite{lin2020localsgd}: ten
steps of exact synchronisation as a warm-up, then local steps, with the ranks'
weights averaged by the number of samples each processed, every epoch ending
on a synchronisation, and the optimiser's moments averaged with the weights
every tenth round. It never adds epochs or changes the batch or the learning
rate. The bar for accuracy is one-sided: the final validation loss may be at
most 1\% higher than one device's, as a mean over three seeds, on every test
model; a lower held-out loss is a more accurate model, though a gap below
$-5\%$ is treated as changed training dynamics and looked at rather than
passed.

The first version followed the DiLoCo paper's outer optimiser, Nesterov
momentum 0.9 at an outer learning rate of 0.7, and failed that bar. At
momentum 0.9 the outer step settles at $0.7/(1-0.9) = 7$ times the averaged
change. The paper synchronises every few hundred steps; over Wi-Fi this system
synchronises every 2 to 64, so the script's learning rate was in effect
multiplied by seven, and an interval adapted to drift made it worse, since more
drift shortened the interval and applied the oversized step more often. The
paper's settings failed at every interval tried, even at one synchronisation
per epoch (the small transformer $+21.7\%$ at 156 local steps). Plain averaging
--- outer learning rate 1, no momentum --- passes. In a lab of two
containers on the LAN and Wi-Fi profiles, three seeds each, the gap to one
device was $+0.64\%$ and $+0.61\%$ on the GPU example's network (a four-layer perceptron), $-2.14\%$ and
$-2.09\%$ on the same perceptron in the training example at its CPU sizing, and $+0.18\%$ and $+0.50\%$ on a
small transformer, each within the spread of exact synchronisation's own gap;
each rank sent 9.1, 10.7 and 1.4\,MiB against 81.1, 98.9 and 21.7\,MiB with
exact synchronisation, nine to fifteen times less. On an idle host (one seed),
the run took 15.2, 10.4 and 19.1\,s against 20.0, 14.6 and 22.7\,s with
exact synchronisation on LAN, and 18.9, 14.1 and 22.9\,s against 41.8, 43.7
and 35.9\,s on Wi-Fi, where one container took 27.9, 16.9 and 26.7\,s.

The interval depends on the ring's size. Plain averaging every 64 steps passed
at two and three ranks but failed at eleven. In in-process runs, on the same three
models and the same bar, the largest interval that passed on every model was
32 steps at two ranks, 16 at three and 4 at four; from five ranks no interval
passed, because at eight ranks the transformer failed at every interval down to
2 and an outer learning rate below 1 was worse. That table is the
default, held identically by the daemon and the shim. An explicit
\texttt{-{}-ddp-sync fast} beyond four ranks still runs, at $H=4$, and says once
that the ring is past the validated size. That accuracy falls as ranks are
added is itself a finding: fast synchronisation helps the two to four machines
of a small group and not a crowd of phones. In-process measurements of the remedies the
literature offers --- keeping each rank's batch so the global batch grows,
drift correction, compressed exact synchronisation, and retuning the interval
and outer step per ring size --- were measured: of those, only exact synchronisation with rank-16 PowerSGD \cite{vogels2019powersgd} compression and error feedback kept every model within 1\% of one device at 4, 8 and 11 ranks (worst mean $+0.18\%$), at $3.2\times$ fewer bytes than int8 exact on the perceptrons and with every step synchronised; keeping each rank's batch (with or without learning-rate scaling \cite{goyal2017imagenet, hoffer2017trainlonger, johnson2020adascale} or doubled epochs), SparseLoCo \cite{sarfi2025sparseloco}, top-k \cite{aji2017sparse}, FedProx \cite{li2020fedprox}, rank-4 PowerSGD and outer learning rates of 1.25 or more all failed.

\textbf{Choosing fast synchronisation automatically.} By default a run asks
for ``auto''. The lead daemon switches a ring to fast synchronisation once,
only when every rank has reported, the ring is not pinned to a size or in the
middle of a join, the ring is within the validated size, and the predicted
fast step, inflated by 10\%, beats both the exact split and one GPU. Every rank
then switches at the same step boundary after the exact warm-up, at the
interval for its size, and rank 0 prints one line saying why and that
\texttt{-{}-ddp-sync exact} turns it off; a joining rank adopts the ring's
mode. When a join takes an automatic fast ring past the validated size, the
ring returns to exact synchronisation at the next epoch boundary; an explicit
fast ring moves to the interval for its new size. A rank whose local round
runs past four times the ring's median step time skips the round's remaining
batches but counts them, so every rank stays on the same step, and the round
is averaged by samples; since in in-process runs every skipped batch cost accuracy
(a factor of 2 instead of 4: 28--30\% less time for 0.3--1.2\% more loss),
the default only guards against a stalled rank.

\textbf{When a rank dies.} Until October one failed rank failed the whole run,
although the round already closed without it. The client now prints which rank
died and on which host, tells the lead daemon, which stops waiting for that rank
and finishes any round held on it, and the survivors take new shares at the next
epoch boundary. The run fails only if no rank finishes or the user interrupts
it, and the error names the real rank rather than a loop count. Samples are
assigned to ranks by a weighted rendezvous hash \cite{thaler1998rendezvous}
rather than the hash-modulo routing of the parallel map, which would move most
samples when one rank left; the rendezvous hash keeps each survivor's share
exact and over 95\% of its samples in place. That holds for a lost machine; a
rank whose script fails now stops every rank at once. Losing rank 0's machine
still ends the run, because its daemon holds the synchronisation, but the
survivors now stop within about 30 seconds with that reason, where in a real
two-laptop run the submitter waited on a ring nobody was running. A script that
slices its own tensors instead of using a data loader is not re-spread.

\textbf{When a machine comes back.} A rank whose machine returns, or a new
eligible node, joins the running ring at the next epoch boundary instead of
sitting idle. The client watches the nodes and starts a rank there; the joiner
loads the lead's model and optimiser snapshot through the lead daemon, and the
shim's world size and
rendezvous-hash shards grow to include it, so about $1/n$ of the data moves. The
daemon's averaging group grows with it. Only data-loader scripts can grow; a
script that slices its own tensors gets one line saying so. The refit now runs
once per synchronisation and reaches every rank, where it used to hand new
shares to one rank per cadence. For each epoch it missed, the joiner runs one
real batch from its data loader during which backward passes, optimiser and
gradient-scaler steps, synchronisation and step counting do nothing, so a
script's loop variables exist afterwards and nothing trains twice; its output is
marked as catch-up until its first real epoch. The snapshot now carries the
model's buffers too, copied in after the catch-up batches, so batch-normalisation
statistics come from the lead. Losing rank 0's machine still ends the run. In
a lab of two containers sharing one GPU a returning rank joined the ring
\textbf{4}\,s after its node's daemon started.

\textbf{Starting together.} On a two-laptop ring, rank 0 trained while rank 1
was still receiving its closure, so every synchronisation waited for it. The
first synchronisation is now a barrier: every rank must reach the opening weight
broadcast --- environment imported, script at its first optimiser step ---
within a configurable wait of five minutes by default. Ranks still missing are
dropped and named, and no step waits on them; while it waits, rank 0 says which
rank on which host it is waiting for, every 30 seconds. The barrier's time is
reported apart from synchronisation, since counting it there once produced
advice built on a single 2.5 minute wait. A late rank is refused without failing
the run and can rejoin through a data loader as above. With a 30 second wait and
the second rank's link throttled to 1\,Mbit/s, rank 0 trained alone after

torch gloo and NCCL back-ends were removed, so this channel is the only one.

\section{The Cost Model}
\label{sec:cost}

Interception is only worthwhile when the cluster actually wins, so numerical
work is gated. Writing $b$ for the payload in bytes, $\phi$ for its arithmetic
intensity in floating-point operations per byte, $\rho$ for the number of times
the data crosses the link, $B$ for link bandwidth and $K$ for the number of
participating nodes, divisible work is distributed only when

\begin{equation}
\label{eq:cost}
\underbrace{\frac{b\phi}{R}}_{\text{compute locally}}
\;>\;
\underbrace{\frac{\rho\, b}{B}}_{\text{move it}}
\;+\;
\underbrace{\frac{b\phi}{R' K}\times 1.3}_{\text{compute remotely}}
\end{equation}

where $R$ is the local throughput, $R'$ the remote throughput, and the factor
$1.3$ charges 30\% overhead against the ideal parallel speedup. Matrix
multiplication is priced at about 200\,GFLOP/s with $\rho = 5$; pandas work at
1\,GFLOP/s. Work that cannot be divided --- an SVD or eigendecomposition, priced
at about 1.5\,GFLOP/s and sent whole to one worker --- moves when the transfer
costs less than half the local computation, since it frees the origin entirely.

The checks run in order. At least two nodes and 32\,MB of payload are required.
Then, \textbf{if the working set does not fit in local memory, the work goes to
the cluster} whatever the transfer costs, and a matrix multiplication the
cluster cannot take either raises an error naming the size and the remedy rather
than falling back to a local run that would exhaust the machine; this was added
after an 8192-square product drove a 14\,GB machine to 194\,MB free and the
kernel killed the desktop session. If any peer reports a GPU, $R'$ is six times
$R$, the figure measured on a small batch rather than the larger saturating one.
The inequality is then evaluated at an optimistic 10\,Gbit/s; if offloading loses
even there, the work stays local without measuring anything. Otherwise bandwidth
is \emph{measured} by pushing 64\,MB through the real dispatch path, cached for
five minutes; if the probe fails, the answer is to stay local. Low-intensity
pandas work ($\phi < 8$) is not distributed below 512\,MB.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.11_cost_model.png}}
    \caption{Decision regions of Equation~\ref{eq:cost} for the pandas path
    ($\rho = 1$, $R = R' = 1$\,GFLOP/s) at three nodes on a 500\,MB/s link.
    Grouped aggregation and joins have low arithmetic intensity, so they are
    distributed only above 512\,MB. The NumPy path uses the same inequality with
    its own throughputs and is not drawn.}
    \label{fig:cost}
\end{figure}

The consequence for dense matrix multiplication is counter-intuitive and worth
stating. Local BLAS runs at roughly 200\,GFLOP/s, which a CPU cluster's transport
cannot beat at practical sizes, so the model keeps it local --- measured against a
four-core peer, local won by 25 to 100 times across four shapes and the model
chose local every time. An earlier version of the project made this a law: the
example suite failed if a matrix multiplication was ever seen leaving the
node. That was a fact about one rig written down as a rule, and it would have
failed on the first cluster with a GPU. The rule is gone; matrix multiplication
now ships when it does not fit locally, when a GPU peer makes the model favour
it, or when forced, and the example instead times the same product locally
and checks that the choice made was not the slower one. Singular value
decomposition, two orders of magnitude slower locally, does ship.

\section{Fault Tolerance}
\label{sec:ft}

The invariant is that using the cluster is never worse than not using it. Five
independent layers enforce it for parallel work; a training ring that loses a
rank continues on the survivors (Section~\ref{sec:intercept}).

\begin{enumerate}[leftmargin=*, label=\arabic*.]
  \item \textbf{The race.} Chunks are dealt alternately to the local side and the
  cluster, and results fill a slot table first-wins. Idle local cores re-run any
  chunk the cluster has not yet returned, and the call returns only once the
  local side has covered every item. A completely dead cluster therefore
  degrades to a plain local pool.
  \item \textbf{Per-primitive fallback.} Every intercepted call is wrapped; any
  exception falls back to the original implementation. The one deliberate
  exception is a matrix multiplication that fits neither locally nor on the
  cluster, which raises (Section~\ref{sec:cost}).
  \item \textbf{Peer fallback.} A failed peer is skipped for the remainder of
  that chunk and the next candidate tried; if all fail, the work runs locally.
  A peer that is merely slow is raced by a local copy of its part, and the first
  to finish wins.
  \item \textbf{Worker respawn.} A dead warm worker is restarted, falling back to
  a one-shot process if that fails.
  \item \textbf{Rescheduling.} A failed job is placed again with backoff doubling
  from 2 seconds to a 2 minute ceiling, on an untried node first and at most
  three times; a node that refused the closure is skipped, and a dead node is
  told apart from a lost network first. Waiting for room never drops a task; a
  cancelled one is not retried.
\end{enumerate}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.92\textwidth]{\figpath{fig_4.12_race_timeline.png}}
    \caption{Racing local and remote work. The local side is always able to
    finish alone, which is what makes the guarantee unconditional.}
    \label{fig:race}
\end{figure}

Memory is bounded at the same time: a parallel-map request larger than a node
can grant is forwarded to a healthier peer, one exceeding 40\% of that memory
is split into sequential chunks rather than refused, and a request body is capped
at the smaller of 2\,GiB and half the daemon's memory budget.

\section{Resource Estimation}

Tiers are consulted in order, the first that yields a value winning: an
explicit override; the largest peak memory from the last five runs of the same
script, plus 20\%; or per-library baselines plus 100\,MB for the interpreter. The
estimator also has a tier based on input file sizes, but every caller currently
passes no input files, so that tier is never reached. The default when nothing
is known is 512\,MB.

The historical tier closes a feedback loop. The worker samples the job's process
tree while it runs and records the peak, and that measurement sizes the next
run's admission request.

\section{Seeing What the Cluster Does}
\label{sec:observe}

Most of what a daemon did was visible only in its log. The work of
October made it visible without adding a daemon endpoint beyond the two for
background mode.

\textbf{An events feed.} \texttt{pipedpeer events} prints, in plain language,
what this machine's daemon has done: peers joining and leaving, links made and
the reason a peer has no path, leases, jobs started, finished and cancelled,
environments sent and imported, keys trusted, and parallel work received and
forwarded. Node identifiers are replaced by host names, repeated lines are
collapsed, and a follow mode prints events as they happen. It reads the daemon's
log, which mixes three formats from two logging libraries, with the project's
own parser; the daemon gained one log line for each event that had none, and its
log times now carry seconds. The feed is per machine: a sender sees what it sent
and to whom, and a receiver who sent what.

\textbf{Load on screen.} Each node's heartbeat always carried its load; the
node table and the terminal dashboard now show cores and CPU use, free memory,
and the GPU's name, utilisation and memory, and the dashboard adds the last few
events and a status line. A peer with no direct path is listed under the table
with its reason, even when no peer is reachable. \texttt{connect} ends with
connected, partly connected or failed, giving each missing machine's reason and
fix.

\textbf{A real dry run.} The check-only flag used to take a lease and cancel it.
It now builds the environment where Nix is present, lists imports with no
package, names the parallel calls in the source that can spread (a regular
expression over the script, since a Python parser would need a Python on the
submitter), and reports the memory estimate, the GPU and ring choice, where the
job would go and how much of its closure that node holds, ending ready or not
ready with the reasons. Without Nix the build is reported as skipped, not
failed.

\textbf{A run summary.} Every run except a detached one ends with at most eight
lines: where it ran, the environment build time, what happened to the closure
(already present, a partial send, or a full or cold send with size and time),
the script's time and peak memory, how its items spread across machines, the
files that came back, and the total, or the moment it was cancelled. The spread
comes from a receipt the shim prints on its error stream at exit, with items
counted by where they ran; the client hides that line and parses it. The
receipt now also counts the items the executing machine ran itself, including a
chunk it re-ran after a peer failed.

\textbf{What each machine spent.} The claim that the sender stays free needed
proof on screen. The summary gains two lines, sampled once a second from the
kernel's process statistics and from the executing node's health endpoint: this
machine's average CPU use, the memory it added and whether it used a GPU, and the
same for the node, with GPU utilisation and peak VRAM where there is one. From a
lab container that sent a parallel-map script away, they read ``CPU 22\% avg,
RAM +69 MB'' for the sender and ``CPU 31\% avg'' for the node. A training ring
prints one such line per machine. A sampling failure prints a warning and drops
the line; it never fails the run.

\section{Later Work}
\label{sec:later}

A run on real machines at the college on 14 October 2026 --- two laptops,
two laboratory PCs on routed subnets and a phone hotspot --- found the address
problems of Sections~\ref{sec:discovery}--\ref{sec:nat}, the
training problems of Section~\ref{sec:intercept}, and a list of annoyances.
This section covers the rest of what changed in answer.

\textbf{Fewer commands, one file, one port block.} Twenty-eight commands became
thirteen: set-up, invite, connect, run, status, dashboard, web page, jobs,
attach, start, stop, doctor and uninstall. Configuration is one file holding the
secret, the introducers and the node's role. The ports moved, in one break
together with the identity change, to a single block: 4242 for the daemon API
(TCP) and discovery (UDP), 4243 for direct links and 4244 for the introducer.

\textbf{Set-up.} Every nightly build is published under its own version, and the
installer takes a version so that every machine in a cluster runs the same
build; it checks the checksum, installs the binary system-wide and runs
set-up. Set-up creates the secret before the daemon first starts, opens the four
ports, offers to start pipedpeer at boot as a systemd user service, and marks
anything the user must do with a coloured \emph{action needed} line. After
\texttt{connect}, the common environments build in the background, so the first
run starts warm. \texttt{pipedpeer doctor} checks the daemon, the secret, each
introducer and each peer --- telling TCP and UDP reachability apart, since a
router that passed UDP but not TCP explained the unexplained ``unknown'' row
of that run --- the firewall, user namespaces, crun, Nix, the GPU driver,
disk and clock, each with its fix. \texttt{pipedpeer uninstall} removes
everything but Nix.

\textbf{Runs like Python.} A plain run prints only the script's own output; the
stages, placement and interception lines appear with \texttt{-v}, and only
warnings that mean a wrong result or a needed action always print. Arguments
after the script go to the script, and the script's exit code is the command's.
When work left the machine, one line follows giving the total time, the script's
own time, pipedpeer's overhead and where the work ran
(Section~\ref{sec:measure}).

\textbf{The web page and phones.} \texttt{pipedpeer ui} opens the page with the
secret in the URL fragment, so nothing is typed. The page shows the nodes,
recent runs from every machine, each run's timeline and where its work ran, and
a run view with every step of every chunk.

\textbf{Phones with Nix.} An Android phone first joined as a pool-only
worker under Termux \cite{termux}, running parallel chunks with Termux's own Python. It can
now run them from a Nix environment. A set-up script installs Debian through
\texttt{proot-distro} and single-user Nix inside it, creating \texttt{/nix}
itself rather than calling \texttt{sudo}; where that is in place, every
command is forwarded into the Debian root file system and the daemon runs
there. At the pinned package set every ARM path of Python with numpy, pandas,
torch, scikit-learn and joblib is in the public binary cache, so no binary
cache of the project's own is needed: the runtime closure is 67 paths, about
1.5\,GiB unpacked and 395\,MiB to download. The Debian runs under
\texttt{proot} \cite{proot}, and the phone advertises itself as taking chunks
only, which \texttt{pipedpeer doctor} states. Termux's \texttt{proot} does not translate
the \texttt{fchmodat2} system call of Linux 6.6 and later, so the Nix installer
failed inside it on such kernels; on those kernels set-up builds the upstream
\texttt{proot} that has the fix, with a local patch that skips a chmod on
\texttt{/proc} which always failed, until Termux ships it; with it, Nix inside
\texttt{proot} built and imported torch and numpy in an x86-64 Termux. Closures go only to
peers of the same architecture. For a peer of another architecture the node
sends the job's package list, Python version and GPU flag instead; the phone
validates the names, writes and builds its own flake in the background, one at
a time, caches it by the flake's hash, and until it is built answers that it
cannot run the job, never falling back to a Python without the job's
libraries. Where \texttt{proot-distro} and Nix are absent the phone stays a
Termux pool worker and logs why; that worker now also carries Termux's torch
and scipy, and takes a chunk only after importing every module the chunk names,
so a module that is installed but fails to load sends the chunk elsewhere.
With an ARM Termux image run under qemu, a laboratory daemon sent a
two-item torch training chunk to the Termux worker, which trained it.

On a real phone, a Samsung Galaxy S20~FE (Android~13, kernel 4.19, Termux from
Google Play), the route needed three fixes before it ran. Termux from Google
Play starts every program through Android's linker, which runs only
position-independent binaries and changes the program's argument list, and a
Go program's own process starts are refused outright; the phone therefore gets
an Android build of the binary, which undoes the argument change and starts
every program through the linker. \texttt{proot-distro}~5.3 binds its own
file descriptors over \texttt{/dev/fd}, which broke every local Nix build, so
the Debian is entered in its minimal mode with the other bindings named
explicitly; and it has no detached login, so the daemon is started in a
session of its own. Set-up then ran end to end. A laptop's CPU script, spread
over that laptop, a second laptop over the internet and the phone, gave the
phone 8 of 192 parallel items with an unchanged checksum, once the phone had
built the job's environment from the cache (27\,s). A torch script training
160 small models gave the phone 6 of them, all converged; with 32 models the
laptops finished before the phone's worker had loaded torch, so the phone took
none and the result was unchanged. On the phone, Nix's Python inside
\texttt{proot} ran the CPU script (without its pandas step, which Termux lacks)
in 62.4, 62.8 and 66.0\,s, against 73.1, 80.8 and 72.8\,s for Termux's own
Python 3.13; the full script took 68.4--72.4\,s inside \texttt{proot}.

\textbf{Speed.} Each change below has a before-and-after figure in
Section~\ref{sec:measure}. Each node's number of chunks in flight follows its
measured round trip instead of a global four; the losing copy of a race is
cancelled, and a peer that lost its last three races stops being raced (in a real
two-laptop run the fast laptop won all 300 races, wasting the peer's work); chunk
size follows the measured transfer cost and shrinks toward the end. The parallel
map's request body was built by repeated concatenation, quadratic in its size,
and is now built once; large functions and globals cross once per peer by hash;
requests are compressed at a level chosen by the measured link speed; numerical
buffers travel out of band; and the link speed is measured from real transfers,
where the cost estimates had been 7 to 37 times too high. Only workspace files
a node lacks are sent; nodes fetch public packages from the Nix binary cache
themselves; and rates per machine and function persist across runs. In training,
gradient upload overlaps the next step's computation, three or more ranks reduce
in a butterfly instead of through one hub, and ranks on one machine average
locally first.

\section{Test Workloads}
\label{sec:workloads}

Ten dispatch scripts exercise placement and concurrency. Seven example
workloads cover a standard-library parallel map, a map over a lambda,
scikit-learn with \texttt{joblib}, NumPy linear algebra, out-of-core pandas,
torch data-parallel training and file synchronisation, and a
walkthrough runs them across three machines on three unrelated networks. A
three-node container lab and a lab with unequal CPU quotas provide the
single-host environments used in Chapter~\ref{chap:results}. Benchmark harnesses
measure parallel maps against hand-tuned pools, the work-sharing policy,
distributed training, matrix multiplication decisions, closure transfer and
interception start-up; a cross-network acceptance script checks that peers on
different networks link directly; and two scripts audit the tests themselves
(Section~\ref{sec:res-tests}).

Three rigs were added in October. A NAT lab places each node on its own private
network behind a router container --- two cone and two symmetric translators ---
with the introducer on a public network, and asserts that cone pairs punch and
take work, that a cone--symmetric pair links by the birthday search, that the
symmetric pair is reported unreachable with its reason, and that a multi-user
Nix node set up once takes work from a node that joins later without a prompt.
A laboratory-layout lab puts containers on one bridge network as a college LAN, with
the host's own daemon as the GPU machine and introducer and one container on
multi-user Nix standing in for the lab's Ubuntu machines; a two-container lab
shares the host's one GPU between two nodes for the training ring. One script
combines every kind of intercepted work, and five scripts written the way a
student would write them stand in for code the system has never seen.

\textbf{Evaluation setup.} Every laboratory figure in this chapter comes from
worker daemons in containers on one host. In the plain laboratory the
containers share the host's processor, memory and loopback interface; it
measures correctness, overhead, cache behaviour and fault handling, and it
\emph{cannot} measure multi-machine speedup, because moving processor-bound
work between containers on one host cannot make that host faster. Where a
figure depends on speed or on the network, each container is given a fixed
processor and memory limit and the links between containers are shaped by
\texttt{tc netem} to the latency, bandwidth and loss of a LAN, a Wi-Fi network
or a 5G link, with up to 5\% loss; speedup is then one container against $N$
containers of the same size. Training accuracy under each synchronisation
setting is measured in-process, with several ranks trained side by side on one
machine and their validation loss compared with one device's; training scaling
uses CPU training in the containers, with the synchronisation cost measured
under the same link profiles, and the one GPU gives single-GPU baselines. Real
hardware appears in two places: the recorded measurements between real machines
(Section~\ref{sec:res-recorded}), which carry their provenance, and two laptops
connected over Tailscale \cite{anderson2020nat}, the realistic worst case across the internet.

\section{Work Crosses Node Boundaries}

With distribution forced, every one of five runs of a 48-item parallel map
reported, in its own receipt, 18 items completed on three other daemons and the
rest locally, with an identical checksum each time. The NumPy workload moved its
34\,MB singular value decomposition to one worker, as the unsplit cost model
allows. Its matrix product is written with the \texttt{@} operator, which is not
intercepted (Section~\ref{sec:intercept}), so it ran locally without consulting
the model at all.

The project's own pool benchmark, run against the laboratory, is the honest
counterpart: plain Python took 0.17\,s, a hand-tuned pool 0.17\,s, and the
untouched script under PipedPeer 0.24\,s with 12 of 48 items run on the cluster.
On one host, distribution can only add overhead, and it did --- within the
project's $3\times$ never-slower budget. Section~\ref{sec:res-recorded} reports
the same benchmark between real machines.

\section{Fault Tolerance}
\label{sec:res-ft}

The fault-injection harness fans an 80-item parallel map across the laboratory,
waits until a worker is holding chunks, kills it, and requires the run to finish
correctly with work recorded as having left the submitting process. It was
strengthened after August, when it was found to prove nothing: its kernel could
not then be shipped, so the local pool did all the work and a kill changed
nothing.

\textbf{In the October run it failed.} The job was placed on the submitting
host, which already held the closure, so nothing was sent; the freshly created
workers never received the closure; and since parallel work is offered only to
peers that can run it, the shim ran all 80 items locally. No worker ever held a
chunk, and the harness reported failure by its own rule. The likely cause is
that the closure is pushed to peers only after an upload, so a job placed on a
node that already holds its closure never seeds the others; this reading of the
log has not been verified further.

The guarantee that remains evidenced is the one the tests establish: every
remote chunk failing still yields correct results, and a run with a dead remote
completes (Table~\ref{tab:whatproves}). The August run of the earlier harness
completed correctly after a worker was killed, but that harness was later shown
not to have distributed any work, so it is not cited as evidence here.

\section{Measurement Method and the Address-Book Phase}

\textbf{One record, two views.} Every run now keeps one record of timed steps
--- serialising, compressing, sending, queueing, computing, receiving and
deserialising each chunk on each machine, building and sending the environment,
each training synchronisation round, and the script itself --- written by the
shim, the daemon and the client into the job's directory. Work done by the shim
is never counted as the script's time; it used to be, which is how the quadratic
request body went unnoticed. The simple view is one line printed after a run
that used another machine; the detailed view is available from \texttt{-v}, the
job history, the web page, and as CSV or JSON, including a single command that
exports every run since a date.

payload from 1\,KB to 2\,GB, one to eight nodes, item count and cost per item,
link profile, loss, a speed spread of up to ten times between nodes, and a cold

8-bit encoding and ranks per node. Each step's growth is fitted on a log-log
scale from the run records, and a step whose exponent exceeds the expected one by
more than 0.15 is treated as a defect.

\textbf{Real points.} Runs between two laptops connected over Tailscale are

honest summary is that PipedPeer occupies a different point on the curve rather

cost, code change and network configuration. BOINC \cite{anderson2004boinc} is closest in spirit, having
pioneered volunteer computing, but it is a platform for specific projects each
with its own server infrastructure rather than a general executor.

\section{Conclusion}

PipedPeer runs an unmodified Python script on other machines with no cluster to
configure, reproduces its environment exactly, distributes the parallel work
inside it without the user touching the source, and joins machines on different
networks with one command and no relay, keeping them joined when their
addresses change. The contributions are:

\begin{enumerate}[leftmargin=*, label=\arabic*.]
  \item \textbf{The store path as a cluster-wide cache key, and the store path as
  the unit of transfer.} Pinning an exact package set makes an environment's
  content-addressed name identical on every machine and on any day, so a worker
  that holds an environment pays nothing for it (23.41 seconds cold against
  0.83 seconds warm in the container lab), and a worker that holds part of it
  receives only the paths it lacks (7 of 43 paths, 86\% fewer bytes, between two
  real machines).
  \item \textbf{Transparent interception with work shared by measurement.} The
  parallel primitives a script already uses are substituted at import time.
  Kernels travel as source or, for lambdas and closures, by value. Parallel maps
  are divided by a makespan solver over measured peer rates, and numerical work
  moves only when the cost model says moving it is cheaper than computing it.
  \item \textbf{Joining across networks without a relay.} An introducer that
  never carries data, router port mapping, a candidate race over one shared
  socket, a birthday-collision fallback for the hardest pair of NATs, and
  mutually authenticated QUIC links that the rest of the system sees as ordinary
  nodes.
  \item \textbf{Placement without a scheduler.} Hard filters followed by a
  bounded score, executed in the submitting client, with a three-phase lease
  providing atomic reservation and crash recovery through expiry, against memory
  budgets that every daemon on a machine respects together.
  \item \textbf{A degradation guarantee that is tested, not asserted.} Five
  independent layers ensure that a remote path has a working local path beneath
  it; the tests show a run completing correctly when every remote chunk fails;
  and a mutation audit that disables 95 features one at a time is caught by the
  test suite in every case. The end-to-end fault-injection run did not
  distribute work on this report's laboratory and remains to be repeated.
\end{enumerate}

The part most worth defending is still the refusal to distribute. Interception
that shipped everything it could intercept would be slower than plain Python on
most workloads. The project repeatedly measured its own features and kept them
off, or changed them, when the measurement disagreed: gradient averaging moved
into the daemon when the blackboard design made training 21 times slower; a
coarser synchronisation interval that ran ten times faster stays opt-in because
it trained a worse model, though that measurement predates fixes to how weights
were averaged and batches split, so its successor is promoted only on its own
evidence; work is divided by measured speed because dividing by
headcount was slower than not distributing; and a rule that dense matrix
multiplication must never leave the node was replaced by a check that the choice
made was not the slower one, because the rule would have been wrong on the
first cluster with a GPU.

\section{Limitations of the Current System}

\begin{itemize}[leftmargin=*]
  \item \textbf{No relay.} Two machines between which no direct path exists ---
  for example two carrier networks that both allocate a new port per destination
  --- cannot work together. Such a peer is reported and routed around.
  \item \textbf{Python only.} Other runtimes would need their own environment
  packaging and their own interception layer.
  \item \textbf{Linux workers.} The sandbox, cgroups and the store are
  Linux-specific. The private-store seed is built for x86\_64 only.
  \item \textbf{A parallel script needs its submitter.} A remote job survives its
  submitter vanishing and can be attached later (Section~\ref{sec:sandbox}), but
  a script whose parallel work is spread runs on the submitter, so that machine
  must survive the job.
  \item \textbf{A training ring needs rank 0's machine.} A ring continues
  without any other rank, but rank 0's daemon holds the synchronisation, and
  re-spreading a dead rank's data needs a data loader; losing rank 0 stops the
  run with a plain reason.
  \item \textbf{GPUs are NVIDIA only in practice}; AMD devices are detected but
  have no ROCm build of torch, and Intel integrated graphics never count.
  \item \textbf{Phones take parallel chunks only}, and are slow at it: a
  phone builds a job's environment itself, one job at a time, on the CPU, and
  on a short torch script the laptops finished before the phone had loaded
  torch.
  \item \textbf{Fast synchronisation is for small rings.} Synchronising every
  $H$ steps holds accuracy at two to four ranks; from five ranks no interval
  passed in in-process runs, so automatic mode keeps such rings exact.
  \item \textbf{Dependencies outside the package set.} An import that neither the
  table nor the package set knows is reported before the run rather than dropped
  silently (Section~\ref{sec:env}), but the job still needs the user to name a
  package for it.
  \item \textbf{Interception gaps.} Only the \texttt{map} of a process-pool
  executor is intercepted, not \texttt{submit}; grouped aggregation on
  categorical keys is never split; and numerical work under 32\,MB never leaves
  the node, by design.
  \item \textbf{A per-machine view.} The events feed shows one machine's
  daemon; there is no cluster-wide view.
  \item \textbf{A partial sandbox.} Memory is limited per job, but the job runs as
  user 0 inside the container with the host's network, without a seccomp filter,
  and isolation is skipped with a warning on a node lacking \texttt{crun} or user
  namespaces (Section~\ref{sec:sandbox}).
  \item \textbf{Measurement.} The single-host lab cannot measure speedup, and the
  multi-machine figures in this report were recorded by hand during development
  rather than by a repeated, controlled experiment
  (Section~\ref{sec:notmeasured}).
\end{itemize}

\subsection*{Defects found while preparing this report}

Writing the measurements down found defects twice. The August pass found three,
all since fixed: the shim imported torch at start-up, taxing every job about
1.7\,s; the sandbox benchmark gave neither sandbox a root filesystem, so every
one of its runs had failed; and the laboratory scripts could not be run twice.
The shim start-up check now runs in continuous integration.

The October pass found the following, which are recorded here rather than
corrected, since this report documents the system as it stands:

\begin{enumerate}[leftmargin=*, label=\arabic*.]
  \item When the user's home directory is itself a version-controlled
  repository, the build directory --- moved from the system temporary directory
  into the user's cache directory --- falls inside it, Nix refuses the generated
  flake as untracked, and the coordinator retries the job indefinitely. The
  measurements in Chapter~\ref{chap:results} were taken with the cache directory
  pointed outside the repository.
  \item Three tests fail, rather than skip, on a machine without torch.
  \item Two of five runs of one benchmark failed with the worker's output stream
  closed early (\texttt{stdout scanner: read |0: file already closed}) and were
  rescheduled; the cause was not investigated.
  \item On a freshly created laboratory, a job placed on the submitting node,
  which already held its closure, never pushed the closure to the workers, so
  its parallel map stayed local and the fault-injection harness could not run
  (Section~\ref{sec:res-ft}). The cause is inferred from the log and not
  verified.
  \item Reading the code for this report raised further suspected defects that
  were not exercised: compressed parallel-map items whose flag the daemon does
  not carry forward, a memory-constrained reply path that answers in a different
  framing from the one the shim reads, receipts that count forwarded work as
  local, removal of one internet peer deleting every loopback forwarder, the
  shared secret being attached to subnet-wide health probes, and the
  firewall-opening commands running without elevated privileges. They are listed
  for the developers in the repository's documentation notes.
\end{enumerate}

Most of these have since been fixed. The build now runs outside the user's
repository; the three tests skip without torch; the fresh-laboratory failure was
traced to every worker refusing the broadcast closure for want of a trusted key
and fixed as Section~\ref{sec:trust} describes; and the compressed-item flag, the
reply framing, the receipt's count of locally run items, the forwarder removal,
the secret sent to subnet probes and the unprivileged firewall commands were
each fixed in a commit of their own. The early-closed output stream was the
daemon reaping a job before its output readers had drained the pipes; it now
waits for them.

\section{Security}
\label{sec:security}

The previous version of this report stated that PipedPeer had no
authentication, no authorisation and no transport encryption. That is no longer
true, and Section~\ref{sec:trust} describes what replaced it: a shared secret on
every route, sent only to hosts that prove they hold it; pinned TLS on the
daemon port; QUIC links across networks authenticated by node keys, with each
hello bound to its session and the secret; and closures signed by the node that
built them, whose keys reach system Nix through a root-owned helper that can do
nothing else.

What remains is still significant and is stated plainly. The secret is optional,
and a daemon without one accepts any request that reaches it, which means
arbitrary code execution for anyone who can reach the port. With a secret, every
holder of it can run code on every node; there is no per-user authority, and
jobs themselves can read the secret. TLS on a local network is trust on first
use and can be downgraded to plain text by an attacker who can break the
handshake. The list of keys trusted to sign closures is not bound to an
authenticated identity, and with the key helper any holder of the secret can
get signed paths trusted on every machine; the submitter's own upload is
imported without a signature check; and the optional registry is
unauthenticated. The repository's security statement describes these limits. The
system is therefore suitable for machines whose owners trust one another, joined
over networks they do not need to trust, which is a substantial change from
before; it is not suitable for a cluster of mutually untrusting participants.

\chapter{Future Scope}
\label{sec:future}
% ============================================================

\begin{itemize}[leftmargin=*]
  \item \textbf{Closing the security gaps.} Binding trusted signing keys to the
  identities that authenticated a link, requiring TLS rather than preferring it,
  checking signatures on every import path, and authorisation finer than one
  shared secret.
  \item \textbf{A relay of last resort}, for the peer pairs that no direct path
  can join, without making it the default data path.
  \item \textbf{Locality-aware placement.} Placement currently scores capacity
  only. Accounting for which node already holds the input data, as iDDS
  \cite{idds2025} does, would reduce transfer for repeated work.
  \item \textbf{Topology-aware placement.} Whole jobs are placed on scalar
  metrics, blind to network distance; link cost is measured only where work is
  divided. A graph-structured representation \cite{zhao2023} would address this.
  \item \textbf{Submitter fault tolerance for parallel scripts.} A remote job
  can already be detached and collected later; a script whose parallel work is
  spread cannot yet outlive its submitter, and a training ring cannot yet
  outlive rank 0's machine.
  \item \textbf{A cluster-wide view}, merging every machine's events (the web
  page already merges every machine's runs).
  \item \textbf{More accelerators}: AMD through ROCm, and a phone worker that
  needs no Termux.
  \item \textbf{Memory escalation} on out-of-memory (gradient accumulation,
  checkpointing, lower precision), and training that survives losing its lead
  machine.
  \item \textbf{Fast synchronisation for larger rings.} Keeping accuracy past
  four ranks --- a growing global batch, drift correction, compressed exact
  synchronisation, or retuning the interval and outer step per ring size, offered
  as opt-in tuning levels or as the default where they pass the same bar --- and
  synchronising the model in staggered fragments (Streaming DiLoCo \cite{douillard2025streaming}).
  \item \textbf{Additional runtimes} beyond Python.
  \item \textbf{A controlled multi-machine evaluation}, repeating the hand
  measurements of Chapter~\ref{chap:results} as a scripted experiment across
  separate machines and networks, and verifying the per-accelerator ranks on a
  machine with two GPUs.
\end{itemize}
