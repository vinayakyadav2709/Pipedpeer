# A root-owned key helper lets the daemon trust new peers' nix keys

A multi-user nix-daemon accepts a signed closure only if nix.conf lists the signing key, and ignores the per-command keys `narpack.Import` passes from an untrusted user. Setup runs before any peer has joined, so every new machine meant one more sudo on every other machine (983ae2a: a manual trust command). Setup now spends its one sudo installing a helper instead, and the daemon adds each token-proven peer's key itself (`src/internal/nixtrust`, user decision 2026-10-12).

- **What setup installs** (multi-user nix only, `setup.helperInstallScript`): a root-owned copy of the pipedpeer binary at `/usr/local/libexec/pipedpeer-nix-trust` (0755, every parent root-owned and not group/other-writable, checked first); `/etc/sudoers.d/pipedpeer` (0440, checked with `visudo -cf` before it is moved into place) holding `<user> ALL=(root) NOPASSWD: /usr/local/libexec/pipedpeer-nix-trust *`; and one `!include /etc/nix/pipedpeer-trusted-keys.conf` line in `nix.custom.conf` (Determinate) or `nix.conf`. Sudo never points at the user's own binary, which the user can rewrite.
- **What the helper does**: run from that file (`nixtrust.IsHelper` compares inodes first thing in `main`), the binary does only `add|remove <key>...`. Each key must be exactly `pipedpeer-<16 hex>:<base64 of 32 bytes>` with the name matching the key's fingerprint; anything else, including whitespace, newlines or a second option, is refused before any file is read. It writes only `/etc/nix/pipedpeer-trusted-keys.conf` (one `extra-trusted-public-keys` line, temp file and rename), dedupes, drops lines it would not have written, and restarts nix-daemon only when the key set changed.
- **Who calls it**: the daemon, when a key it collected is not trusted, or when a closure arrives signed by a verified sender key system nix does not trust yet, before the import (`daemonapi.warnUntrustedKeys`, from the poll and from `importSignedClosure`; `sudo -n`, retried at most every 15 minutes per key, with a warning when it fails); `pipedpeer setup` and `connect`, which install the helper first if `sudo -n -l` says the user cannot run it. There is one trust path: nothing else writes nix configuration.
- **Removal**: `pipedpeer uninstall` removes the helper (with the rest of pipedpeer), the sudoers file, the keys file and the include line, and restarts nix-daemon. Nothing removes a single key automatically: pipedpeer has no revocation, and a peer that goes stale may come back. `remove` exists for that day.
- **Cost**: the user account (and so anyone with the cluster token, through the daemon) can make system nix trust any well-formed key, which lets signed store paths into a store other users of the machine share. That is what the old manual trust command already allowed; it is now automatic ([SECURITY.md](../../SECURITY.md)). Adding a key restarts nix-daemon, which drops nix operations in flight on that machine.
